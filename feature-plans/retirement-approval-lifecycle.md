# Feature: Retirement Approval Lifecycle (Phase 2, Cycle 2b)
Status: ready
Created: 2026-08-26

## Summary
Layer an operator decision surface on top of the shipped advisory Retirement Recommender (Cycle 2a). Three additive pieces, ONE cycle: (1) an **LLM explainer** that produces a concise, human-readable "why this symphony is a retirement candidate" over the deterministic recommendation evidence — explains, never decides; (2) an **approve/reject lifecycle** so the operator can act on each recommendation, with the decision persisted in a mutable status keyed to the candidate symphony; (3) on approve, a **deterministic Composer liquidation checklist** (advisory text — the manual wind-down steps + the candidate's current holdings) with **no execution primitive of any kind**. Operator ruling (Gate-2b): the LLM is strictly OUT of the approve/checklist action path; approve/reject are deterministic status writes; the checklist is a deterministic template (no LLM); nothing executes a trade — the operator follows the checklist by hand in Composer.

## Acceptance Criteria
- [ ] AC-1 (explainer module): New `advisors/retirement_explainer.py` — `explain_recommendation(recommendation: dict) -> str | None` takes a Cycle-2a recommendation `raw_response` dict (candidate_id/sibling_id/correlation/ci_lower/composites/gate verdicts/basis_label) and returns a concise plain-text explanation of why the candidate is flagged (redundant with the sibling + weaker composite + which gates passed). Uses the `ai_advisor._build_client()` seam + `model_config.get_advisor_suggestion_model()` (fable-5, cheap) + `client.messages.create(...)` plain text (NOT tool-use), mirroring `advisor_chat.explain_artifact`. D-1 never-raises: any failure returns `None` (honest empty), user-facing error is `type(exc).__name__` only, never `str(exc)`. Read-only — reaches NO DB write, NO trade/exec primitive.
- [ ] AC-2 (explainer runs at producer time, persisted): The 03:45 producer (`_run_retirement_recommender_tick`) calls the explainer per recommendation AFTER the deterministic `build_recommendations()` and BEFORE persist, stamping `explanation` (str | None) into each rec's `raw_response`. The LLM never runs on the render path or the approve/checklist path. `advisors/retirement_recommender.py` stays LLM-free (the explainer call lives in the producer orchestration, not in `build_recommendations`).
- [ ] AC-3 (approval persistence): New migration `038_retirement_decisions.sql` — a small MUTABLE table `retirement_decisions` keyed by a UNIQUE `candidate_id` (the stable natural key; a persistently-flagged pair recurs with the same candidate_id, giving "decide once, persists across nights"). Columns (additive-first, NULLable + DEFAULT): `id` PK, `candidate_id` TEXT UNIQUE NOT NULL, `sibling_id` TEXT, `approval_status` TEXT NOT NULL DEFAULT 'pending' (CHECK/validated `pending|approved|rejected`), `decided_at`, `updated_at`. Accessors in `database.py`: `upsert_retirement_decision(candidate_id, *, approval_status, sibling_id=None) -> bool` (mutable UPSERT keyed by candidate_id), `get_retirement_decisions() -> list[dict]` (all rows, for the live-join), `get_retirement_decision(candidate_id) -> dict | None`. Parameterized, WAL, D-1.
- [ ] AC-4 (live-join at render): `ai_advisor_tab()` builds `{candidate_id: decision_row}` once from `database.get_retirement_decisions()` and stamps each recommendation card's `approval_status` (+ `_decision`) in-place — mirroring the incubation `_incubation_by_hash` live-join (`app.py:6125`). Status is read FRESH from the mutable table at render, NEVER from the frozen `advisor_observations` row. A recommendation with no decision row shows `pending`.
- [ ] AC-5 (approve/reject routes): New retirement-SPECIFIC routes `POST /ai-advisor/retirement/approve` and `POST /ai-advisor/retirement/reject` (NOT the frontrunner `/ai-advisor/proposal/approve`, which reaches `save_symphony`). Each parses `{candidate_id: str}`, writes the status via `database.upsert_retirement_decision(...)`, returns `{success, approval_status, error}`. CSRF/auth via the global hooks; D-1 (`type(exc).__name__`, 200); NOT in `_SETTINGS_WRITE_ALLOWLIST`; reach NO Composer/exec/`LIVE_EXECUTION`/trade primitive. Approve writes status ONLY — it does not itself render or execute the checklist.
- [ ] AC-6 (deterministic checklist): New `advisors/retirement_checklist.py` — `build_checklist(recommendation: dict, bot_state: dict) -> dict` returns a deterministic, advisory wind-down checklist for the candidate: the candidate symphony id (+ name if resolvable from bot_state), its current holdings tickers from `bot_state[candidate_id]["logic_holdings"]` (defensive: weight may be float or `{"weight": x}`; use the ticker set), and the fixed manual steps (advisory prose the operator performs in Composer). NO LLM. NO exec primitive, no import of `composer_draft_client`/`alpha_bot_execution`, no order/submit call. **Honest off-hours degrade:** when `logic_holdings` is empty (03:00/weekend/flat — the documented runtime-field caveat), the checklist renders the steps + an explicit "current holdings unavailable (off-hours) — view live positions in Composer" note, never fabricated tickers.
- [ ] AC-7 (panel extension): The Overview-tab retirement panel (`templates/ai_advisor.html` `retirement-recommendations-panel`) gains, per card: the persisted `explanation` text (honest "explanation unavailable" when absent); the live `approval_status`; Approve/Reject buttons (hidden/disabled once decided) wired via a `retDispatchDecision(action, candidateId)` JS fn mirroring `frDispatchProposalAction` (CSRF header, POST, disable-on-submit); and, on an APPROVED card, the deterministic checklist rendered read-only. All fields HTML-escaped (no `| safe`), design tokens only.
- [ ] AC-8 (safety boundary — extended no-trade scan): Extend/parametrize `tests/security/test_retirement_recommender_no_trade_boundary.py` (or a sibling) to source-scan EVERY new module (`retirement_explainer.py`, `retirement_checklist.py`) for NO reachable exec/trade primitive: no import/call of `composer_draft_client`, `alpha_bot_execution` trade fns, order/submit, no `LIVE_EXECUTION` read/write. The new routes are asserted NOT in `_SETTINGS_WRITE_ALLOWLIST`. NOTE the deliberate refinement: the checklist is advisory TEXT that necessarily describes liquidation — the scan forbids executable trade CODE PATHS, NOT advisory string content (unlike the 2a scan's identifier-token ban on the pure-math module). Name new code identifiers to avoid the forbidden tokens where practical; the safety guarantee is "no exec call path reachable," proven by the scan + a call-graph assertion.
- [ ] AC-9 (empty/degenerate + D-1): No recommendations → panel unchanged (honest empty, no explainer/checklist). Explainer API down → cards render with the deterministic evidence + "explanation unavailable"; the feature is fully usable without the LLM. A candidate with empty holdings → checklist degrades honestly. Every new module/route never raises (D-1).

## Architecture
- **`advisors/retirement_explainer.py`** (NEW): LLM explainer (fable-5, `_build_client` seam, `messages.create` text, D-1). Consumes a rec `raw_response` dict; returns `str | None`. No DB write, no trade path.
- **`advisors/retirement_checklist.py`** (NEW): deterministic checklist builder from a rec + `load_state()` holdings. Pure-ish, no LLM, no exec.
- **`database.py` + `migrations/038_retirement_decisions.sql`** (NEW): mutable `retirement_decisions` table (candidate_id UNIQUE) + upsert/get accessors. Additive-first.
- **`app.py`**: producer orchestration (explainer loop before persist, AC-2); the live-join in `ai_advisor_tab()` (AC-4); the two new retirement approve/reject routes (AC-5); the checklist assembled for approved cards at render (calls `retirement_checklist.build_checklist`). `_fetch_retirement_recommendations` unchanged (returns raw_response incl. the new `explanation` key).
- **`templates/ai_advisor.html` + `static/ai_advisor.js`**: panel extension (explanation, status, buttons, checklist) + the `retDispatchDecision` JS.
- **Reuse:** frontrunner approve/reject route + JS shape (`frDispatchProposalAction`), incubation live-join pattern (`_incubation_by_hash`), `advisor_chat.explain_artifact` LLM pattern, `ai_advisor._build_client`, `model_config.get_advisor_suggestion_model`. Do NOT reuse the frontrunner `/proposal/approve` route (reaches save_symphony).

## Design-System Mapping
No formal component library; reuse the existing `.retirement-rec-card` / `.prism-*` / frontrunner-proposal-card token classes + button styles in `templates/ai_advisor.html`. Approve/Reject buttons mirror the frontrunner proposal buttons' styling. No raw hex; honest empty-states mirror the Market-Prism pattern.

## Edge Cases
- No recommendations → no explainer/checklist/buttons (honest empty).
- Explainer API down / timeout → `explanation=None` → "explanation unavailable"; deterministic evidence + approve/reject still work.
- Off-hours empty `logic_holdings` → checklist shows steps + "holdings unavailable" note, never fabricated.
- Same candidate re-flagged with a different sibling next night → decision persists by candidate_id (approve/reject about the CANDIDATE's retirement). [PM-ASSUMED — surface at ship gate.]
- Double-submit / already-decided → buttons disabled; upsert is idempotent (keyed by candidate_id).
- A decision row exists for a candidate no longer in the latest batch → harmless (live-join only stamps cards that render).
- CSRF token missing/expired on the JS POST → refetch pattern (mirror frontrunner JS).
- `logic_holdings` weight shape variance (float vs `{"weight": x}`) → defensive ticker-set extraction.

## Security Considerations
- **Safety boundary (primary):** NO exec/trade primitive in any new module or route. Extended source-scan (AC-8) + call-graph proof. The approve route writes a status only; the checklist is advisory text; the explainer is read-only. No route in `_SETTINGS_WRITE_ALLOWLIST`; no `LIVE_EXECUTION`.
- **LLM data exposure:** the explainer sends only the recommendation's own numeric evidence + symphony ids to Anthropic — no secrets, no credentials. D-1 error contract; never echo `str(exc)`.
- **CSRF/auth:** new POST routes covered by the global CSRF + auth hooks (401 unauth); parse only `candidate_id` (validated against known recommendation candidate_ids where practical).
- **Injection:** parameterized DB accessors only; migration additive-first, NULLable+DEFAULT, reversible-safe. No user-supplied SQL/paths.
- **XSS:** explanation + checklist + ids all HTML-escaped in the template (no `| safe`).

## Testing Strategy
- Unit (`tests/advisors/test_retirement_explainer_*.py`): explainer prompt shape (fed the raw_response), text extraction, D-1 (client raises → None; API error → None, no `str(exc)` leak), model accessor used (fable-5 seam), NO DB/trade path. Mock the `_build_client` seam (no live Anthropic).
- Unit (`tests/advisors/test_retirement_checklist_*.py`): deterministic output for known rec+holdings; off-hours empty-holdings honest degrade; weight-shape variance; NO LLM, NO exec import (source-scan).
- DB (`tests/database/test_retirement_decisions_*.py`): migration 038 applies; upsert idempotent keyed by candidate_id; status validation; get/live-join shape; WAL/parameterized.
- Route/panel (`tests/app/test_retirement_approval_*.py`): approve/reject 401-unauth, CSRF, status write, D-1, NOT in allowlist, GET-of-panel live-joins status, approved card renders the checklist, buttons hidden once decided, all escaped.
- Security (AC-8): extended no-trade source-scan over the 2 new modules + the new routes' allowlist exclusion + a call-graph assertion that approve/checklist reach no exec primitive.
- Property/adversarial (quant-test-writer): the LLM is never reachable from the approve/reject/checklist code paths (structural); the explainer never gates a recommendation (a None explanation still renders the card + buttons).
- Live PM gate (post-merge): real render of the panel with a seeded approved recommendation (explanation + checklist), a real approve→status→re-render cycle, and a probe that the explainer produces sensible text on a real recommendation (fable-5, one call).

## Decisions
| Decision | Rationale |
|----------|-----------|
| Approval persistence = incubation-style live-join marker (new `retirement_decisions` table), NOT frontrunner-style full-payload table | The recommendation payload already lives (append-only) in advisor_observations; only the mutable STATUS needs storage. Live-join by candidate_id mirrors incubation. |
| Join key = `candidate_id` | The only stable natural key in the flattened raw_response (no hash/id); recurs across nights for a persistently-flagged pair → "decide once, persists." [PM-ASSUMED] |
| Retirement approve = a SEPARATE route, status-write only | The frontrunner `/proposal/approve` reaches `save_symphony` (creates a symphony) — the opposite of retirement; never overload it. Retirement reaches NO Composer/exec. |
| Explainer runs at 03:45 producer time, persisted into raw_response | Codebase pattern (heavy work off-hours, render reads persisted); keeps the LLM off the render path AND out of the approve/checklist action path (operator ruling). |
| Explainer fed the rec's own raw_response, not build_reasoning_context | The raw_response evidence is self-contained + pair-scoped; build_reasoning_context is single-symphony-scoped + costlier with no pairwise evidence. |
| Explainer model = fable-5 (get_advisor_suggestion_model) | Lightweight explanation → the cheap suggestion-family knob, not the opus synthesis knob. |
| Checklist = deterministic text (no LLM), honest off-hours degrade | Operator ruling (deterministic template, no LLM in action path). logic_holdings is empty off-hours → never fabricate. |
| No-trade scan for new modules = "no exec CALL PATH" (allows advisory liquidation TEXT) | The checklist necessarily describes liquidation; the safety guarantee is no executable trade code, not banning a word in a string. |

## Scope Boundaries
- **IN**: the LLM explainer module (+ producer wiring + persistence into raw_response); migration 038 + `retirement_decisions` accessors; the live-join; the two retirement approve/reject routes; the deterministic checklist module; the panel/JS extension (explanation + status + buttons + checklist); extended safety tests.
- **OUT**: ANY execution/liquidation/trade primitive (the operator manually acts in Composer); the LLM anywhere in the approve/reject/checklist action path; reusing/altering the frontrunner `/proposal/approve` route; changes to `advisors/retirement_recommender.py`'s deterministic math (the explainer wiring lives in the producer, not in build_recommendations); the 1-minute execution path (`alpha_bot_execution.py`/`math_engine.py` ZERO diff); Phase 3 (`sleeves/` audit).
