Open questions, with the PM's proposed defaults:
- Q1 "May two concurrent requests both parse the file?" Default: no. Concurrent misses share one computation; a second request waits for the first instead of parsing again.
- Q2 "What identifies an unchanged cache file?" Default: the resolved file path plus its size and modification time, re-checked on every request with no time-based expiry.
- Q3 "Latency bound?" Default: on a production-sized fixture (at least 11 symphonies and a cache file of at least 70 MB), a cold request parses the file at most once, and a warm request parses it zero times and takes under 0.5 s. A concurrent /api/performance during a warm preconditions request is not delayed by more than 0.5 s against running alone. Leave the cold-request wall-clock bound to the architect to measure, stated as a ratio (at most 1/5 of the current per-symphony cost).
- Q4 "Memory?" Default: between requests keep only the derived per-symphony daily return lists (small), never the parsed history dict.
