# Plan — Phase-2 Binding Preconditions (a/b/c/d) — Gate Before Any Build

> Phase 2 is authorized **if and only if** four named preconditions ALL pass.
> Precondition (d) may be structurally unsatisfiable — **stopping permanently at
> Finalist A is a full success, not a project failure** (synthesis §0, §5.1).

| Field | Value |
|---|---|
| Feature | A committed precondition document and four committed gate artifacts. None of the Phase-2 implementation plans (`simulate-forward-paths/`, `cvar-cosignal-hysteresis-trigger/`, `priority-resolver-cvar-cosignal/`, `tier1-seed-determinism/`) may proceed to build until this gate clears. |
| Phase | 2 (entry gate, blocking) |
| Owner agent-type | `risk-engine-specialist` + `quant-code-reviewer` (gate) + `quant-risk-researcher` (precondition d design) |
| Source-of-truth refs | `docs/handoff/decision-science-council-synthesis.md` §5.1 (four preconditions), §0 (stopping at A is full success), §5.7 (B-2/B-3 deferred gates); `docs/handoff/decision-science-v3-and-divergence-evaluation.md` §A.4 H-4 (precondition (a) — M2's role limited to "can raise a gross kill flag"); `docs/handoff/council-attack-rubric.md` B-2 ★, B-3, K-2 ★ |
| Why | Without a structural precondition gate the Phase-2 schema, simulator, and trigger get built speculatively. The four preconditions are the council's binding contract that says "if any of these fail, Phase 2 does not proceed and the system stays at Finalist A permanently" (§5.7 verbatim). |
| Deliverables | (1) `docs/handoff/phase-2-precondition-checklist.md` — the four preconditions as a committed checklist with the status of each, pre-registered acceptance criteria, named owner, and the "what we do if this fails" branch. (a) **M2 evidence — KILL-or-INCONCLUSIVE ceiling.** Per H-4: M2 can ONLY raise a gross kill flag against Phase 2; it cannot advance Phase 2. The acceptance criterion is "M2 has run a full shadow window AND no gross uninformativeness was observed AND a separately-powered discriminating test design has been authored." (b) **Gate-zero tail-data audit.** A data audit (phase0 OQ-1) of AlphaBot's history that confirms enough genuine sub-5% tail observations *per regime cluster* to power *some* discriminating validation. **This audit can kill Phase 2 outright.** Acceptance criterion: documented per-regime-cluster tail count ≥ a pre-registered floor. (c) **Latency + bucket arithmetic (B-2/B-3).** A *measured prototype* proves the Tier-1 pre-open batch finishes with margin before the first cycle, AND the regime buckets are populous enough to simulate from. **If latency arithmetic does not clear OR buckets are too thin, Phase 2 does not proceed.** (d) **Powered validation design exists** — OR the trigger ships diagnostic-grade-permanent (never as a calibrated budget). Per §2.3 this may be structurally unsatisfiable (~1,000-tail-observation requirement is a decade+ away). (2) `tests/integration/test_phase_2_preconditions_gate.py` — a meta-test that opens the checklist document, asserts each precondition has a written status; if any status is "FAILED" or "UNRESOLVED," the test refuses to import any `phase-2/*` build artifact (a no-go-zone enforcer). (3) Operator runbook step: re-run the precondition gate on every Phase-2 cycle entry. |
| Dependencies | M2 must have completed Phase 1 and a full shadow window before precondition (a) is evaluable; the gate-zero tail-data audit must be authored by `quant-risk-researcher`; the latency/bucket prototype must be authored by `risk-engine-specialist`. |
| Golden-fixture tests required | The checklist document and the no-go-zone meta-test ARE the gate artifacts. No golden-fixture data tests here — the test is structural. |
| Definition of Done | (a) Four preconditions documented, each with pre-registered acceptance criteria. (b) Meta-test enforces the no-go-zone — any Phase-2 build artifact imported with an unresolved precondition fails the test loud. (c) **The "Phase 2 may never unlock" framing is in the checklist verbatim** — a future PM cannot quietly graduate "INCONCLUSIVE" to "PASS." (d) The "stopping at A is full success" framing is in the checklist's header — Phase-2 abandonment is the documented expected branch, not a failure. |
| Risk callouts | **R1 — A future cycle softens the precondition wording**: the checklist is committed and any edit to acceptance criteria requires a full council re-evaluation, not a single-PM decision (rubric K-3). **R2 — Precondition (d) marked "PASS" with a hand-waved validation design**: the design must be authored by `quant-risk-researcher` and include a power calculation that confronts the ~1,000-observation wall directly. **R3 — Precondition (a) gets pulled forward to "M2 shows incremental signal"** — explicitly REJECTED per H-4. |
| Out of scope | The actual Phase-2 implementation plans (each is a separate document under `phase-2/`); the Phase-2 schema migrations (deferred per persistence-architect's converged plan §3.2); the legacy-drop ceremony at last-symphony cutover (H6 in the converged plan). |
