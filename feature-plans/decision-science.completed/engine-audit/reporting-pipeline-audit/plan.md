# Plan — Engine Audit: Reporting Pipeline Audit (`reporting.py` — Discord + QuickChart)

| Field | Value |
|---|---|
| Feature | Audit of `reporting.py`'s Discord webhooks and QuickChart embeds for: (a) response-body redaction (overlay gate 7); (b) URL hygiene (overlay gate 5 — no hardcoded webhook URLs); (c) failure swallow vs raise (must not fail a cycle on a telemetry-class outage); (d) replay determinism (reporting must not bleed wall-clock into a value that feeds back into a decision); (e) the four-part S-3 display contract for M2's CVaR — if M2 is *also* rendered to Discord (operator surface), the bias-warning element (d) must be on the Discord card too. |
| Phase | Engine audit (post-Phase-1) |
| Owner agent-type | `quant-code-reviewer` (audit lead) + `flask-dashboard-specialist` (display contract enforcement, since `reporting.py` shares the display surface contract) |
| Source-of-truth refs | `docs/handoff/council-attack-rubric.md` standing gates 5, 7; project CLAUDE.md (reporting is operator-visible — same redaction rules); `docs/handoff/decision-science-council-synthesis.md` §4 (S-3 binding); the logging-redaction plan; existing `reporting.py` |
| Why | M2's bias warning (S-3 element d) is load-bearing on **every** operator surface that renders the CVaR number — Discord card, QuickChart embed, dashboard panel. If Discord renders only the number without the bias warning, the operator anchors on a reassuring-looking number that is systematically too mild — the exact failure mode S-3 (d) exists to prevent. |
| Deliverables | (1) `docs/handoff/engine-audit/reporting-pipeline-findings.md` — each Discord card and QuickChart embed enumerated; per-row, the redaction status, the URL hygiene, the failure mode (swallow / raise), and (for M2 cards) the S-3 four-part display compliance. (2) `tests/integration/test_reporting_no_response_body_echoes.py` — Discord webhook failure path injects a synthetic 500 response with payload; assert the log line carries only the status code and the cycle_id, not the response body. (3) `tests/integration/test_reporting_failure_swallows_in_live.py` — Discord webhook failure does not fail the cycle (matches `record_shadow_observation` swallow precedent — telemetry-class). (4) `tests/integration/test_reporting_no_hardcoded_webhook_urls.py` — grep test: no hardcoded Discord URL or webhook secret in source. (5) `tests/integration/test_m2_discord_card_carries_four_part_s3.py` — Phase-1 conditional: if M2 is rendered to Discord at all, the card payload contains the stderr, the `cvar_n_tail`, the "diagnostic, not a signal" label, and the bias warning. (6) `tests/integration/test_reporting_no_wallclock_feedback.py` — confirms `reporting.py`'s wall-clock reads stay on the telemetry side (timestamps for human readability) and never feed back into a numerical value that any other module consumes. |
| Dependencies | The logging-redaction plan; the M2 plan; the dashboard side-effect ban plan (shared display surface contract). |
| Golden-fixture tests required | Tests 2, 3, 4, 5, 6 are golden-fixture / grep tests. |
| Definition of Done | (a) Findings document is committed; every reporting surface enumerated. (b) Five tests pass GREEN. (c) If M2 is rendered to Discord, the bias warning is on the card — full S-3 compliance, not partial. (d) Telemetry failure swallow is the explicit live-mode policy in reporting. |
| Risk callouts | **R1 — A "short" Discord card omits the bias warning for length**: test 5 fails loud — bias warning is mandatory wherever M2 renders. **R2 — A Discord URL is hardcoded for a "test" run**: test 4 fails — URL must be a config / env variable. **R3 — A failing webhook fails a cycle**: telemetry-class failures swallow in live; test 3 catches a regression. |
| Out of scope | The actual Discord card layout / branding (separate UX cycle); QuickChart pricing / quota (operational concern); the `reporting.py` re-write (a separate refactor cycle if needed). |
