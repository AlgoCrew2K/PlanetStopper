### What exists and is adopted
- The minute scheduler is `run_scheduler()` (`app.py:1427-1443`) on the `schedule` library (`requirements.txt:14`, `schedule~=1.2.2`). In that version `Job.run()` calls the job and only then `_schedule_next_run()`, so a job that raises is never rescheduled and runs again on every `run_pending()` (once a second), while the due jobs sorted after it are skipped for that pass. One raise in the loop ends the thread (`app.py:1441-1443`). This is why the guard below is per job, not only around the loop.
- The engine spawn is `threaded_trigger()` (`app.py:792-793`) starting `trigger_alpha_bot()` (`app.py:776-789`); `subprocess.run(..., check=True)` has no timeout (`app.py:785`), and Q-3 keeps it that way (no kill). The engine's own lock (`database.py:293-318`) stays as it is (S-5.5, engine path zero diff).
- The event fan-out is `_notify_cycle_complete()` (`app.py:726-773`) over `_sse_clients` (`app.py:607-608`); the stream is `sse_events()` (`app.py:2477-2510`). The mask-then-refresh sequence (`app.py:758`, `:763`) stays (plan Earlier criteria, DE-SSE-PUSH-001).
- Account totals: `_StaleFlagDict` (`app.py:513-577`), `_account_totals_last_good` and `_account_totals_last_success_at` (`app.py:586-589`), `_refresh_account_totals()` (`app.py:813-909`), the live Tier-1 stale stamp (`app.py:2350-2354`). Its callers at the ref: the `:00` job (`app.py:1429`, inline on the scheduler thread), the post-cycle thread (`app.py:763`) and the flush-resync thread (`app.py:6403`).
- `/health` (`app.py:392-412`) is auth-exempt through `_AUTH_EXEMPT_ENDPOINTS`; `/api/state` is `get_state()` (`app.py:2513-3513`), whose `_additive` dict (`app.py:2527-2532`) is merged into the frozen, waiting and live branches.
- The calendar is `market_calendar.py` (`is_trading_day` `:41`, `session_close` `:81-104`, `get_market_state` `:107-136`, `REAL_MARKET_OPEN_TIME` `:16`). The engine's blackout and post-mortem windows are computed inline (`alpha_bot_execution.py:634-641`: close minus 7 minutes, close plus 5 minutes); no shared helper exists (`git grep -n "minutes=7" -- '*.py'` returns only that engine line), and the engine file stays zero diff.
- The header label is `updateEngineStatus()` (`static/chrome.js:208-239`); the `/` event handler is the anonymous listener at `static/index.js:1600` inside the file's IIFE (`static/index.js:1`).
- The trajectory cache is `database._shadow_cr_cache` (`database.py:3000`) read by `analytics._get_shadow_cumulative_trajectory()` (`analytics.py:662-756`), invalidated only in `record_shadow_observation()` (`database.py:3027-3029`). `git grep -n "_get_shadow_cumulative_trajectory" -- '*.py' ':!tests'` finds no production caller.

### New primitives (each with the search that found none)
- `CycleRecord`, a frozen dataclass in `app.py` beside `_notify_cycle_complete` (new: `git grep -n "cycle_id" -- app.py` finds no daemon-side run identity; the engine's own `cycle_id` columns are telemetry keys in other formats, `alpha_bot_execution.py:946` `YYYYMMDD_HHMM` and `:1741` ISO, and are not reused). Fields: `cycle_id`, `started_at`, `completed_at` (ISO 8601 with the ET offset), `outcome` (one of the Contract Changes vocabulary, held in `_CYCLE_OUTCOMES`), `changed` (bool), `exit_code` (int or None), `running_cycle_id` and `running_since` (set on a skip only). `event_payload()` returns exactly the five contract keys. This is the one object SD-3 joins: the event, `/health` and plan 05's cycle line all read it.
- `_mint_cycle_id(started_at)`: `<started_at to the second, ISO with offset>#<n>`, `n` counting ids minted in this process for that second under a lock (normally 1, as in the plan's Worked Example). The pidfile singleton (`app.py:668-722`) means two daemons never mint in the same second.
- `_publish_cycle(record)`: the single choke point every engine run and every skip passes through. C1 stores the record as the last cycle and calls `_notify_cycle_complete(record)`; C2 adds the failure history and the skip line. Plan 05 C4 emits its cycle line here, from the same object, in the same `finally` of `trigger_alpha_bot()` that calls it.
- `_now_et()`: the wall clock, `datetime.now(_ET)` read at call time, so both `monkeypatch.setattr(app_module, "_now_et", ...)` and the existing frozen-`datetime` harness (`tests/app/test_held_basis_route_convergence.py:44-109`) replace it. `_monotonic`: a module attribute bound to `time.monotonic`, always called as `_monotonic()`, so tests replace it. All ages (scheduler tick, engine overrun, account-basis grace) use `_monotonic()`, never wall-clock subtraction.
- Engine-running state: `EngineRun(cycle_id, started_at, started_mono)` held in `_engine_run` under `_ENGINE_RUN_LOCK`, with `_begin_engine_run(started_at) -> EngineRun | None` (None when one is running), `_end_engine_run(cycle_id)` and the read seam `_engine_run_state() -> EngineRun | None` (new: no in-process run state exists; the only overlap guard is the engine's 60 s DB lock).
- `market_calendar.rebalance_blackout_start(d) -> time` and `market_calendar.post_mortem_cutoff(d) -> time`, beside `session_close` (new: see the search above). Named constants `REBALANCE_BLACKOUT_MINUTES = 7` and `POST_MORTEM_GRACE_MINUTES = 5`, each with a source comment citing `alpha_bot_execution.py:640-641`, and a tripwire test that parses the engine source for `timedelta(minutes=7)` and `timedelta(minutes=5)` beside `rebalance_blackout` and `post_mortem_cutoff`, so the daemon's copy cannot drift from the engine's.
- `database.read_cycle_markers() -> tuple[str | None, str | None]`: `SELECT json_extract(data,'$.last_successful_cycle_at'), json_extract(data,'$.last_market_close_snapshot.trading_day') FROM bot_state WHERE id = 1` on `get_ro_connection()` (`database.py:98-102`), returning `(None, None)` on any error (new: `load_state()` `database.py:322-328` parses the whole row, 2,039,413 bytes in the audit's production copy, and no targeted read exists; `grep -n "json_extract" database.py` finds only `advisor_observations` reads). It is a read, so `database.py` gains no writer and imports nothing new.
- `_GuardedJobCall`, a `functools.partial` subclass whose `__call__` catches `Exception`, logs one ERROR naming the slot and `type(exc).__name__` (traceback at DEBUG, the model-unpin C9 `_model_warmup_worker` precedent), and returns normally so `schedule` reschedules the job. `_guard(job, label) -> job` rebuilds `job.job_func` as a `_GuardedJobCall` over the same `func`, `args` and `keywords` and copies the wrapper attributes, so `job.job_func.func` is still the registered function (model-unpin C9's slot test reads `job.job_func.func is app_module._start_model_warmup`). Registrations keep the literal `schedule.every()...do(<fn>)` text inside `run_scheduler()`, wrapped as `_guard(schedule.every().day.at("03:00").do(_run_lens_pipeline), "03:00 lens pipeline")`, so the source scans (`tests/app/test_incubation_scheduling.py:68-95`, `tests/app/test_retirement_recommendations_scheduling.py:87-121`, the regex at `tests/ai_advisor/test_cycle4_lens_pipeline.py:938-951`) stay green.
- `_start_account_refresh(reason) -> bool`: starts `_refresh_account_totals()` on a daemon thread named `account-refresh-<reason>` and returns at once; a non-blocking `_ACCOUNT_REFRESH_FLIGHT` lock keeps one minute or startup refresh in flight (a second start logs INFO and returns False). The post-cycle thread (`app.py:763`, name `cycle-refresh`, which `tests/conftest.py` and `tests/realtime_push/conftest.py:53-89` join by name) stays separate, so the call count stays two a minute (NB-7).

### Behaviour by criterion
- AC-1 (C1, S-1.7 in C2): `trigger_alpha_bot(force=False, *, cycle_id=None, started_at=None)` keeps its subprocess call byte-identical (argv, `check=True`, the log file, `PYTHONIOENCODING`), reads `read_cycle_markers()` and the stat of `post_mortems/post_mortem_<ET date of started_at>.json` (`analytics._POST_MORTEMS_DIR`, `analytics.py:70`) before and after the run, takes the exit code (0, `CalledProcessError.returncode`, or None when the spawn itself raised, logged with the type name), and in its `finally` builds the `CycleRecord` and calls `_publish_cycle`. `outcome` comes from the pure `_classify_outcome(started_at, exit_code)`: non-zero or None is "failed"; otherwise the engine's own branch order (`alpha_bot_execution.py:654`, `:678`, `:1027`): not a trading day, before 09:30 or after the post-mortem cutoff is "closed"; from the blackout start to the close is "blackout"; from the close to the cutoff is "eod"; else "cycle". `changed` is true when `last_successful_cycle_at` or the snapshot's `trading_day` differs from the before-read, or the post-mortem file's `(exists, mtime_ns, size)` changed; if either read failed, `changed` is true, so an unknown state refetches (DEC-1, S-1.11). Stage 1 writes its file once a day (`reporting.py:33-36` returns when it exists), which gives S-1.3 true and S-1.4 false. `_notify_cycle_complete(record)` keeps its mask and post-cycle refresh for engine runs, skips both for a "skipped" record (no engine ran, so no account state changed), and puts `("cycle-complete", json.dumps(record.event_payload()))` on each queue. On `/`, the listener becomes the named `handleCycleCompleteEvent(evt)` in `static/index.js`: it parses `evt.data` in a try and skips `loadState()` and `fetchGuardAlphaSummary(_heroWindow)` only when the parsed `changed === false`; unparseable data or a missing key refetches (S-1.9, S-1.10).
- AC-2 (C1): `generate()` registers its queue, then yields `retry: <_SSE_RETRY_MS>` with `_SSE_RETRY_MS = 5000` (DEC-2) before its first wait, so werkzeug writes the status line and headers with that first chunk. Events are written as `event: <name>\ndata: <json>\n\n`; heartbeats stay every `_SSE_HEARTBEAT_S = 15` seconds (a named constant so a test can shorten it).
- AC-3 (C2): every registration is `_guard`ed; the `:00` refresh registration becomes `_start_account_refresh` (from C3), so no Composer call runs on the scheduler thread; the loop is `while True: _scheduler_tick(); time.sleep(1)`, where `_scheduler_tick()` runs `schedule.run_pending()` inside `try/except Exception` (one ERROR line with the type name) and then stamps the tick (`_scheduler_last_tick_mono`, `_scheduler_last_tick_at`). `time.sleep` stays outside the `try`. Slots keep their host-clock times (Q-1, NB-6).
- AC-4 (C2): `/health` keeps `status`, `daemon_started_at` and `last_successful_cycle_at` (still read through `database.load_state()` as at the ref) and adds `scheduler_last_tick_at`, `engine_running_since`, `last_cycle` (`{cycle_id, outcome, completed_at}` or null) and `degraded_reasons`. The pure `_health_degraded_reasons(now_mono)` returns `scheduler_stalled` when the last tick (or, before the first tick, the scheduler's start, or before that the process start `_DAEMON_STARTED_MONO`) is 120 s old or more, `engine_overrun` when a run has lasted more than 180 s, and `engine_failing` when the last 5 spawned runs (a `deque(maxlen=5)` of outcomes; skips excluded) all read "failed" (Q-2 constants `_HEALTH_SCHEDULER_STALL_S = 120`, `_HEALTH_ENGINE_OVERRUN_S = 180`, `_HEALTH_FAILING_RUNS = 5`). Both are assembled by `_health_status()`, which the route calls (Contracts). `last_cycle` is the newest record of any outcome, skips included (accepted by the PM). The Friday post-close run includes the autotuner in the engine process (`alpha_bot_execution.py:1180-1190`), so `/health` reads `engine_overrun` while it runs; no exemption is coded (PM-2, S-4.10). The body carries times, an id and an outcome only.
- AC-5 (C2): `threaded_trigger()` (kept as the `:00` callable) takes `started_at = _now_et()` and calls `_begin_engine_run`. When a run is in flight it builds a "skipped" record with `running_cycle_id` and `running_since`, and `_publish_cycle` writes the skip line through `_log_skipped_minute(record)` (WARNING on the `alphabot` logger: the skip's own `cycle_id`, the skipped minute, `running_cycle_id`, `running_since`) and emits the event (S-1.7). Plan 05 C4 replaces `_log_skipped_minute` with its one cycle line and updates this plan's S-5.1 test (PM ruling). Otherwise it starts `Thread(target=trigger_alpha_bot, kwargs={cycle_id, started_at}, daemon=True, name="engine-cycle")`; a failed `start()` ends the run state and logs one ERROR (S-3.5). `trigger_alpha_bot()`'s `finally` calls `_end_engine_run(cycle_id)` before `_publish_cycle`, each in its own guard, so a publishing fault can never leave the run state set. Nothing kills an engine (NB-5).
- AC-6 (C5): `_engine_phase(now_et, market_state, last_cycle_at) -> str`: "closed" unless `market_state == "open"`; "blackout" from `market_calendar.rebalance_blackout_start(date)` to the session close (half-days included through `session_close`); "opening" from 09:30 until 09:35 (`_OPENING_PHASE_MINUTES = 5`, Q-4) while `last_successful_cycle_at` is absent or earlier than today's 09:30 ET; else "running". It is computed once in `get_state()` and put in `_additive`, so every branch carries `engine_phase`. In `updateEngineStatus`, after the Closed branch and before the Stale check (the SD-13 order recorded in `approach/00-suite.md`), "blackout" sets "Rebalance pause" with the Q-4 tooltip and "opening" sets "Opening" with the tooltip "Scheduled session start; the first cycle is running." (accepted by the PM), both through `textContent` and `title` with `--studio-ink-dim` as the Closed state uses. For the server render (S-6.8), `dashboard()` computes the same `_engine_phase(now, market_state, last_successful_cycle_at)` from the `now` and `market_state` it already reads (`app.py:1670-1672`) and the `bot_state` it already holds, and passes `engine_phase` to `render_template` (`app.py:1815-1819`); `templates/_chrome.html:50-53` renders "Rebalance pause" or "Opening", with the same tooltip in the `title` of `#engine-status`, inside its existing `meta.system_online` branch when `engine_phase is defined` and reads "blackout" or "opening", and is unchanged otherwise, so the pages that do not pass `engine_phase` render as at the ref.
- AC-7 (C3): `_refresh_account_totals()` also stamps `_account_totals_last_success_mono = _monotonic()` beside `app.py:878`. `_account_basis_past_grace()` is true when that stamp is None or at least `_ACCOUNT_BASIS_STALE_AFTER_S = 90` old (Q-5). Tests that seed `_account_totals_last_good` with no stamp keep reading stale, as at the ref. Every writer of the totals stamps the same success time, so the grace holds whichever refresh is in flight: the `:00` refresh, the post-cycle thread and the flush-resync thread (`app.py:6403`, S-7.7) all call `_refresh_account_totals()`. `GET /` reads the same live strip through `get_api_state_dict()` (`app.py:1667-1669`, `:2462`), so its server render gets the grace with no further code (S-7.8; the chip itself is rendered hidden at `templates/index.html:952` and filled by `static/index.js`). ### Contracts exposed (SD-3, and what plans 04 and 05 consume)
The shared record of these names, SD-13's full precedence, the suite's branch names and the note that the daemon `cycle_id` does not join the engine's telemetry `cycle_id` columns are in `feature-plans/refresh-timing/approach/00-suite.md`; this section lists only what plan 02 builds.
- `cycle-complete` data: `{"cycle_id", "started_at", "completed_at", "outcome", "changed"}` from `CycleRecord.event_payload()`; `/api/events` opens with `retry: 5000`.
- The run record: `CycleRecord`, passed by `trigger_alpha_bot()` and by the skip path to `_publish_cycle(record)`, the one place the event, `/health`'s `last_cycle` and plan 05's line read it. `exit_code` is on the record, not in the event.
- Engine-running-since state: `_engine_run_state()` returning `EngineRun(cycle_id, started_at, started_mono)` or None, set through `_begin_engine_run(started_at)` and cleared by `_end_engine_run(cycle_id)`.
- Clocks tests replace: `app._now_et` (wall clock) and `app._monotonic` (ages).
- The skip line: `_log_skipped_minute(record)`, called only from `_publish_cycle` for "skipped", replaced by plan 05 C4.
- `/health`: the added fields above. `/api/state`: `engine_phase`. `portfolio_strip.account_basis_stale`: absent inside the 90 s grace on the live branch.
- Helpers a route can call without a request context (plan 04's `GET /api/header-status` reads both): `_engine_phase(now_et, market_state, last_cycle_at) -> str` (pure; `get_state()` passes its own `now`, `market_state` and `last_successful_cycle_at`), and `_health_status() -> dict` returning `{"status", "degraded_reasons", "scheduler_last_tick_at", "engine_running_since", "last_cycle"}` from the scheduler and run state with no database read. `/health` returns `_health_status()` plus `daemon_started_at` and `last_successful_cycle_at`; neither verdict is computed inline in a handler.

No new dependency, no migration, no new route, no `bot_state` writer, no new auth-exempt endpoint. `math_engine.py` and `alpha_bot_execution.py` carry zero diff.

## Execution Model
One Toxic Pair per cycle, each in its own isolated worktree on its own branch, never the primary checkout (project `.claude/CLAUDE.md` Agent Team Composition and Merge and PR Workflow; worktree discipline as the project memory rules on isolated worktrees and on copying `.env` into a worktree). The test-writer runs `/tdd` against this plan and approach, the implementer runs `/tdd-implement` from the handoff, and `/tdd-finalize` closes the cycle.

- C4 (ET dates, trajectory freshness): pair. Reviewers: `qa`, `code-reviewer`, `api-expert` (`/api/state` dates).

- The plan is Sensitive (money): one `qa` dispatch in hidden mode after approval writes hidden scenarios against C2's head, where the spawn and skip decisions live.
- One doc-gen for the slice after every reviewer passes every head.

Team size: 30 = 5 test-writer + 5 implementer + 2 qa + 1 qa (hidden) + 2 code-reviewer + 1 ux-expert + 1 behavioral-evidence-capturer + 5 api-expert + 3 pipelines-expert + 4 integration-auditor + 1 doc-gen

Test-run governor: every pytest run is a background task with output to a file, at most 4 workers, never `-n auto`, and each slice below is sized to finish under 240 s; a slice that reaches 240 s is split by file before its next run, so no worktree logs two runs of 300 s or more within an hour.
