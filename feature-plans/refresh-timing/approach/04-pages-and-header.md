### Shared client module (new)
`static/request_guard.js`, loaded by `templates/_chrome.html` immediately before `chrome.js` (`templates/_chrome.html:218`), so it runs before every page script on `/`, `/history`, `/performance`, `/settings` and `/ai-advisor` (each page includes the chrome before its own scripts: `templates/index.html:761` before `:1872`, `templates/history.html:265` before `:398`, `templates/performance.html:389` before `:618`, `templates/settings.html:834` before `:1068`, `templates/ai_advisor.html:1198` before `:2968`). It exposes `window.PSRequest`:
- GET side (C1): `issue(key)` and `isLatest(key, n)` (overview SD-6 newest-issued guard, per tab, module memory only); `getJson(url)`, which reads `performance.now()` as `sentAtMono` immediately before its `fetch` and calls `window.receiptTiming(sentAtMono, response)` when the response arrives (RC-3: `{sentAtMono, receivedAtMono, serverNowMs}`, the server time from the `Date` header; `getJson` builds no record of its own), resolving `{ok: true, status, body, timing}` only for a 2xx JSON body, else `{ok: false, status, kind}` with `kind` one of `unauthorized` (401), `http`, `not_json`, `network`; `goLogin()` (`location.assign('/login')`).
- POST side (C2): `csrfToken()` (the tab's one token holder, filled once at `DOMContentLoaded` from `GET /api/csrf-token`); `refreshCsrf()` (single-flight: concurrent callers share one `GET /api/csrf-token`); `noteDaemonStart(iso)` (remembers the first `daemon_started_at` it sees and calls `refreshCsrf()` when a later value differs, Q-2); `postAction(url, init)` (calls `fetch(url, init)` exactly once with the caller's `init` untouched, and resolves `{status, ok, body, refused: 'csrf' | null, tokenRefreshed, networkError}`; on a 403 it awaits `refreshCsrf()` and resolves `refused: 'csrf'`; it never calls `fetch(url, ...)` a second time and has no retry path).
- New because no shared request helper exists: each of eight scripts holds its own `_csrfToken` and its own fetch (`static/chrome.js:4-10`, `static/index.js:14-20`, `static/settings-modal.js:26-32`, `static/settings.js:31-37`, `static/ai_advisor.js:12-18`, `static/ai_advisor_asset_swaps.js:16-22`, `static/ai_advisor_logic_changes.js:18-24`, `static/ai_advisor_chat.js:30` and `:264-272`; search: Grep `csrf-token|_csrfToken|X-CSRF-Token` over `static/` and `templates/`). A per-file refresh would copy the same logic eight times (DC-2). Every 403 in `app.py` comes from the CSRF check (`app.py:379` is the only `abort(` and the only `403` producer; Grep `abort\(|403` over `app.py`), so the module reads any 403 on a POST as the session check's refusal (Risk Register C2).
- Each control keeps building its own `init` exactly as at the ref and passes `PSRequest.csrfToken()` where it passed `_csrfToken || ''`, so URL, method, headers other than the token value, and body are unchanged (S-2.11, NB-2). Each control maps the result to its own fixed text (DEC-1); server refusal messages render through `textContent`.

## Execution Model
Each cycle is a Toxic Pair (one `test-writer`, one `implementer`) in its own worktree under `.claude/worktrees/`, never the main checkout, with `.env` copied in and `git rev-parse --show-toplevel` and `git rev-parse --abbrev-ref HEAD` checked before the first edit (project worktree rule). Cycle branches are `refresh-timing/04-c1` to `refresh-timing/04-c9` and the assembly branch is `refresh-timing/04` (RC-8). Every merge into a cycle branch or into `refresh-timing/04` is done by a test-writer and implementer pair (RC-9): a cycle with several base inputs merges them as its own first commits; each merge into `refresh-timing/04` is an integration task run by a fresh pair, which the suite approach sizes. The PM creates the branch refs, records every SHA and never runs `git merge`. This plan's integration tasks: I1 enters plan 02's tip and `refresh-timing/03` (holding 03 C2, C3 and C5) into `refresh-timing/04` before C1 forks; I2 enters the passed C3 to C8 heads (C2 through their ancestry) before C9 forks; I3 enters C9's head and `main` (holding plans 01, 02, 03, 05 and model-unpin) before the PR. A header-recovery capture across a restart follows RC-10. Reviewers per head, dispatched by the PM in parallel at cycle-complete against one HEAD:
- `qa` and `code-reviewer` on every head (every diff changes code).
- `ux-expert` with `behavioral-evidence-capturer` on the heads that render UI: C1 (header), C2 (button text, alerts, the login line), C3, C4, C5, C6, C7, C8.
- `api-expert` on the heads that add or change a route's answer: C1 (`/api/header-status`), C2 (login refusal), C3 (`/api/history/<days>`), C4 (`/api/performance`), C5 (the run route's body and `/api/frontrunner-build/last-run`), C6 (`/api/armed-symphonies`), C8 (`/api/fleet-alert/dismiss`).
- `integration-auditor` on the same seven heads, each of whose diffs touches a route and the UI that reads it (plan Gates).
- `security-auditor` on the AC-2 and AC-7 heads, C2, C5, C6, C7, C8 and C9 (plan Gates).
- One `qa` dispatch in hidden mode for the plan (Sensitive: security, money), and one doc-gen for the slice after every head passes.

The capturer never clicks a write, trade or spend control. Its never-click list, in every capturer brief: every census POST control (`/settings` Save, modal Save and Go live, Emergency Liquidate Confirm, Cash Now, Force run now, Approve, Reject, Accept, Run build, Run now, Run Claude advisor, the Strategy Builder run, Evaluate on Asset Swaps and Logic Changes, Dismiss, sleeve arm, disarm and delete, flush Confirm, chat Send) and the candidate-alert bell (its click sends mark-viewed; the capturer reaches `/ai-advisor` by URL). Refusals are verified without a click by:
1. the node harness running each real control function against route answers produced by the real app, with a recorder that fails the test on any POST not preceded by a dispatched click and that records every request's bytes;
2. Flask test-client tests with the CSRF check (and for login the auth gate) re-enabled and `app._CSRF_TOKEN` rotated between the page GET and the POST, proving the server's real answer;
3. SC-8 Mode A refusing every operator POST before it reaches the app (ux-overhaul `00-suite.md` SC-8 item 6), and each capture record listing every request the page sent, a POST in it failing the capture;
4. the S-2.9 login line rendered by a `browser` test against the in-process server (`tests/ui/_browser_server.py`) that rotates the token between GET and submit, its screenshot saved under the head's review folder for the ux-expert;
5. the PM's live check on the droplet, which provokes the refused Settings Save across a daemon restart and the Emergency Liquidate blank-token refusal on a dry-run instance (plan DoD; ux-overhaul 04 PM-4).
The capturer may drive page loads, a History bar click (a view), the flush trigger (it sends only `GET /api/armed-symphonies`), gear clicks that open the modal (GETs), and `page.route` interception of GETs (Chart.js CDN aborted, `/api/settings` failed, `/api/autotune-runs` answered with the auth hook's error body).

Tests follow RC-11: named slices expected under 240 s, background runs with output to a file, at most 4 workers, never `-n auto`, browser modules `-m browser -n 0` one at a time; the merge-gate scoped run is itself a list of slices (Merge Criteria).

Team size (the RC-9 integration pairs are sized by the suite approach): 50 = 9 test-writer + 9 implementer + 3 qa + 1 qa hidden + 3 code-reviewer + 2 ux-expert + 2 behavioral-evidence-capturer + 7 api-expert + 7 integration-auditor + 6 security-auditor + 1 doc-gen
