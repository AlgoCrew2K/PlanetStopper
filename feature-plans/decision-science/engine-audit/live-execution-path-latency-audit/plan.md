# Plan — Engine Audit: Live Execution Path Latency Audit (1-minute cadence non-blocking I/O)

| Field | Value |
|---|---|
| Feature | Post-decision-science-changes audit of the per-cycle execution path in `alpha_bot_execution.py` for blocking I/O introduced or aggravated by the Phase-1 changes. The audit produces a per-call-site latency budget map: every new call added by the decision-science work is benchmarked against the 1-minute cadence budget, and any caller that introduces network/disk I/O on the path is flagged. |
| Phase | Engine audit (post-Phase-1) |
| Owner agent-type | `quant-code-reviewer` (audit lead) + `risk-engine-specialist` (latency benchmarking) |
| Source-of-truth refs | project CLAUDE.md architecture constraint 1 (1-minute cadence, no blocking I/O); `docs/handoff/council-attack-rubric.md` B-1 ★ (no blocking I/O on per-cycle path), standing reviewer gate 1 (math-layer change → golden-fixture test); `docs/handoff/decision-science-v3-and-divergence-evaluation.md` §A.3 (H-3 per-cycle write is non-zero non-blocking I/O cost — the H4 helper test runs in this audit too); `alpha_bot_execution.py` cycle loop (~`1063-1496`) |
| Why | M2 introduces a per-cycle `INSERT` into `cvar_diagnostics`. The H4 helper plan benchmarks the write in isolation; this audit ensures the **integrated** cycle (with M2 plus any other Phase-1 additions) still fits the budget. Catching latency drift on the integrated path is harder than at the unit level; a separate audit lane is the safe place. |
| Deliverables | (1) `docs/handoff/engine-audit/execution-path-latency-map.md` — every new call site on the cycle's hot path, with (a) the function called, (b) whether it performs network I/O, disk I/O, or DB write, (c) a measured wall-clock budget (median + 99th percentile), (d) the integrated cycle latency before and after the call. (2) `tests/integration/test_cycle_latency_under_one_minute_budget.py` — runs a full cycle (with M2 enabled) over a captured fixture; asserts the wall-clock is well within the 1-minute budget (target: median < 5s on the CI runner; 99th percentile < 15s). (3) `tests/integration/test_no_new_blocking_io_on_cycle_path.py` — static call-graph test from the cycle entry point: every function reachable on the per-cycle path either (i) is annotated `@pure`, (ii) is the H4 telemetry helper (the one accepted exception per H-3), or (iii) is in a documented exception list with reviewer sign-off. (4) An audit row for each call site reachable from the cycle entry, asserting the H4 helper is the **only** new DB write on the path (no other Phase-1 PR snuck in a write). |
| Dependencies | The H4 helper plan; the M2 plan; the live-vs-replay safety boundary plan. |
| Golden-fixture tests required | Test 2 is a fixture-backed integration latency test (captured cycle inputs); test 3 is a structural call-graph test. |
| Definition of Done | (a) Latency map is committed with every new call site represented. (b) Tests 2, 3 pass GREEN. (c) Any new I/O-introducing call on the path requires a documented exception with reviewer sign-off — flagged loud by test 3. (d) The H4 helper's per-cycle write is the only accepted exception (H-3 ruling). |
| Risk callouts | **R1 — A "small" Composer API call slips onto the path**: rubric B-1 ★ fail; test 3 catches structurally. **R2 — Latency drift goes unnoticed over months**: test 2 runs on every CI; a drift trend triggers reviewer attention. **R3 — CI runner is too noisy**: 99th-percentile fallback; the integration test is marked `@pytest.mark.benchmark` and runs in a dedicated stage if needed. **R4 — Phase-2 simulator's Tier-1 batch is conflated with the per-cycle path**: the audit's call-graph test scopes to the cycle entry only; Tier-1 is out-of-band per its design (precondition (c) covers Tier-1 latency separately). |
| Out of scope | Tier-1 pre-open batch latency (Phase-2 precondition (c)); test execution time (separate concern); CI infrastructure (separate concern); Composer/Alpaca client retries (composer-alpaca-integration audit if needed — see separate audit plan). |
