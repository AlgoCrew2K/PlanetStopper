### Session lifetime and revocation (AC-2, AC-3, AC-4)

Search: `git grep -n -i -E "revoc|revoke|session_generation|issued_at|PERMANENT_SESSION|permanent_session_lifetime"` over tracked `*.py` (tests included, `.claude/` excluded) finds nothing; the only session readers are the auth hook (`app.py:307`) and the login GET (`app.py:321`), and the only writers are login (`app.py:384-385`) and logout (`app.py:392`). No existing primitive records a server-side session state, so the following are new.

- Session issue time. Login (`app.py:384-385`) keeps `session.clear()` and `session["authenticated"] = True` and adds `session["issued_at_ns"] = max(_session_now_ns(), _revocation_floor_ns() + 1)`. The `max` keeps a login made in the same clock tick as a logout valid on a coarse clock. The session stays non-permanent (no `session.permanent`), so Flask never re-signs it on later requests and the lifetime is absolute from login (R-12, S-2.3).
- Lifetime. A pure `_session_lifetime_hours(raw: str | None) -> int`: `None` or `""` gives 12 with no log line; a value matching `[0-9]+` whose integer is 1 to 720 gives that integer; every other value gives 12 and logs one WARNING on the `alphabot` logger naming `DASHBOARD_SESSION_LIFETIME_HOURS` and the 12-hour default, never the raw value or any secret. Constants `_SESSION_LIFETIME_DEFAULT_HOURS = 12`, `_SESSION_LIFETIME_MAX_HOURS = 720`. Module level, after the daemon log handler is attached (`app.py:616-638`) and before `_LOGIN_FORM_EXPIRED_LINE` (`app.py:641`): `app.permanent_session_lifetime = timedelta(hours=_session_lifetime_hours(os.environ.get("DASHBOARD_SESSION_LIFETIME_HOURS")))`. `load_dotenv(ENV_FILE_PATH)` (`app.py:95`) has already put the `.env` value in the environment. `app.permanent_session_lifetime` is the one authority: the validity check reads it at request time, and Flask 3.1's `open_session` uses it as the signature's maximum age (Trigger F-3), a second bound with the same value. The key is not added to `_SETTINGS_WRITE_ALLOWLIST` (`app.py:9474`).
- Revocation record. Migration `migrations/040_dashboard_session_revocation.sql` (one above the highest file, `039_close_account_totals.sql`), appended to the end of `database._MIGRATION_FILES` after `"039_close_account_totals.sql"` (`database.py:1878`), creating a single-row table on the pattern of `033_candidate_alert_state.sql`: `dashboard_session_revocation(id INTEGER PRIMARY KEY CHECK (id = 1), revoked_before_ns INTEGER NOT NULL DEFAULT 0, updated_at TEXT)`. Additive, idempotent (`CREATE TABLE IF NOT EXISTS`), state DB only, migration only (no `init_db` mirror, as 039). `database.run_migrations` runs at import through `init_db` (`database.py:288`), so the daemon applies it at start. Two accessors in a new section placed before `# --- H1: Schema Migration Runner ---` (`database.py:1830`):
  - `get_session_revocation_floor_ns() -> int` reads `revoked_before_ns` for `id = 1` over `get_ro_connection()` (`database.py:99`), returns 0 when no row exists and raises on any other failure. It deliberately does not swallow errors as `get_candidate_alert_viewed_marker` does (`database.py:1684-1702`), because a swallowed failure here would let revoked sessions through.
  - `record_session_revocation(floor_ns: int) -> int` upserts with `ON CONFLICT(id) DO UPDATE SET revoked_before_ns = MAX(revoked_before_ns, excluded.revoked_before_ns), updated_at = datetime('now')` (the monotonic idiom of `set_candidate_alert_viewed_marker`, `database.py:1705-1732`), commits and returns the stored value; it raises on failure. Two simultaneous logouts can never move the floor back (S-3.5).
- In-process floor (`app.py`, new helpers placed after `_clear_failed_attempts`, `app.py:256-258`, before `_is_api_or_xhr`, `app.py:261`):
  - `_PROCESS_STARTED_NS = time.time_ns()` at import.
  - `_session_revoked_before_ns: int | None = None` and `_SESSION_REVOCATION_LOCK = threading.Lock()`.
  - `_session_now_ns() -> int` returns `time.time_ns()`; it is the clock seam tests patch.
  - `_revocation_floor_ns() -> int`: on first call, under the lock, reads `database.get_session_revocation_floor_ns()` once; if the read raises, logs one ERROR line naming the exception type only and uses `_PROCESS_STARTED_NS`, so every session issued before this process started is refused and a new login is served (S-3.8, Q-4). Later calls return the cached value, so an authenticated request performs no database read (no blocking read per poll).
  - `_revoke_sessions_issued_before(now_ns: int) -> bool`: under the lock, raises the in-memory floor to `max(floor, now_ns)` first, then calls `database.record_session_revocation`; returns `False` and logs one ERROR line naming the exception type only when the write raises. The in-memory floor is raised before the write, so a failed write still refuses every earlier session for the life of the process (S-3.7, S-4.7, Q-4).
  - `_session_issue_is_valid(issued, now_ns) -> bool`: `True` only when `issued` is an `int` and not a `bool`, `issued > _revocation_floor_ns()` and `now_ns - issued <= app.permanent_session_lifetime.total_seconds() * 1e9` (a request at exactly the lifetime is served; one past it is refused, the plan's "longer ago than").
  - `_session_is_valid() -> bool`: `session.get("authenticated") is True and _session_issue_is_valid(session.get("issued_at_ns"), _session_now_ns())`. A cookie issued before this change carries no `issued_at_ns` and is refused (S-3.9, D-7).
- Auth hook (`app.py:269-313`): the check at `:306-308` becomes `if _session_is_valid(): return None`; the unauthenticated outcome at `:310-313` is unchanged (302 to `/login`, or 401 `{"error": "unauthenticated"}` for `/api/` and XHR). The fail-closed misconfiguration branches (`:282-304`) are unchanged and still run first (S-2.18).
- Login GET (`app.py:319-323`): `if _session_is_valid()` replaces `session.get("authenticated")`, so an expired or revoked session gets the form (S-2.13). It passes `notice=_LOGOUT_NOT_DURABLE_LINE` when `session.get("logout_notice") == "revocation_not_durable"`, where `_LOGOUT_NOT_DURABLE_LINE = "Signed out. Other sessions are ended until the daemon restarts."`. The flag is a field of the signed cookie (not a query string, so no link can make the page claim it), kept until the next successful login clears the session (Items Raised 5).
- Logout (`app.py:389-393`) becomes `@app.route("/logout", methods=["GET", "POST"])`, one view function `logout`:
  - GET renders `login.html` with `confirm_logout=True` and ends no session (S-5.1, S-5.3).
  - POST calls `_revoke_sessions_issued_before(_session_now_ns())`, then `session.clear()`, sets `session["logout_notice"] = "revocation_not_durable"` when the write failed, and returns `redirect(url_for("login"))`. It reads no request body (S-5.13).
- `logout` leaves `_AUTH_EXEMPT_ENDPOINTS` (`app.py:190-195`, comment at `:190-192`). The hook is then the only place that decides validity: a GET or POST to `/logout` without a valid session (none, expired or revoked) gets the hook's 302 to `/login` and the handler never runs, so nothing is revoked (S-3.6, S-5.7, Q-3). The exempt set shrinks; nothing is added to it (Items Raised 7). CSRF is unchanged: `_csrf_before_request` (`app.py:644-662`) checks every POST; `_validate_csrf` (`app.py:426-478`) reads the form field only for the `login` endpoint, so `POST /logout` accepts the header token only (S-5.9, Q-1) and a same-site or cross-site `Sec-Fetch-Site` is refused (S-5.5). Auth runs first (`app.py:269`), so an expired session's POST gets 302 or 401 before the CSRF check.
- Event stream (`app.py:5245-5279`): in the view body, inside the request context, `enforce = _auth_check_enabled` and `issued = session.get("issued_at_ns")` are read before `generate()` is built, because the generator runs after the view returns, outside the request context. In the loop, before each `yield` of an event (`:5264`) or heartbeat (`:5266`), `if enforce and not _session_issue_is_valid(issued, _session_now_ns()): return`; the `finally` (`:5267-5274`) still removes the queue. The retry line (`:5260`) stays first. `queue.get(timeout=_SSE_HEARTBEAT_S)` (`:5263`, `_SSE_HEARTBEAT_S = 15` at `:949`) bounds the time to notice a revocation or expiry to one heartbeat (AC-4). With the suite's auth gate off (`tests/conftest.py:362-379`) `enforce` is `False` and every existing stream test is unchanged.

## Execution Model

Four Toxic Pair cycles run at once, each a fresh `test-writer` (RED author and closer) and a fresh `implementer` on its own branch and worktree, because no cycle reads another's committed code:
- C1 (session lifetime, revocation, event stream, logout): `test-writer` + `implementer`. The largest cycle (AC-2 to AC-5, 54 scenarios); auth, CSRF and a migration, so security-sensitive (never trivial).
- C2 (Cash Now removal): `test-writer` + `implementer`. Client-only edits plus three baseline re-records with their own producers.
- C3 (tenure market gate and explainer sentence): `test-writer` + `implementer`.
- C4 (`/health` caller classes): `test-writer` + `implementer`. Split from C1 against the PM's three-cycle expectation: AC-1 shares no production function, template or test file with the session work (its only shared file is the boundary-scan module, at a different hunk), so a fourth pair finishes 19 scenarios in parallel instead of lengthening C1's round, at the cost of two agents.

`quant-test-writer` is not added: no cycle edits math, money arithmetic or the engine.
