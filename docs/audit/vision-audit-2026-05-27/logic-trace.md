## §1. Per-symphony engine flow narrative

The daemon is a single Python process started by `python app.py`. On startup `app.py:2502-2508` enforces a daemon singleton (`enforce_singleton_or_exit`) and spawns one daemon thread running `run_scheduler()`. The scheduler (`app.py:301-307`) registers three jobs via `schedule.every().minute.at(":00")`: `threaded_trigger` (the engine spawn), `_refresh_account_totals` (NAV refresh), and a daily 02:00 `_run_trigger_retention` prune. At :00 of every minute, `threaded_trigger` (`app.py:222`) forks a non-blocking daemon thread that runs `trigger_alpha_bot()`, which `subprocess.run`s `[sys.executable, "alpha_bot_execution.py"]` and tee's stdout/stderr to the daemon log (`app.py:208-219`). The subprocess-per-tick design is deliberate: it isolates engine crashes from the Flask process and keeps the dashboard read-only — *the scheduler is the only legal engine spawner* (the comment at `app.py:1552-1553` and the disabled `/api/trigger` handler at `app.py:1550-1554` encode this in code).

Inside `alpha_bot_execution.py`, the per-cycle loop iterates **per-symphony, per-account** — never per-portfolio. For each symphony the engine snapshots Composer holdings, computes `current_return`, refreshes high-water mark (`bot_state[symphony_id]["high_water_mark"]`, `alpha_bot_execution.py:1098-1110`), runs `math_engine.run_monte_carlo` keyed on a `cycle_id`-derived seed (`alpha_bot_execution.py:1112-1119`; `math_engine.derive_cycle_mc_seed` at `math_engine.py:762-769` makes the seed deterministic across daemon restarts), then walks the six math layers (vol-scaling → time-squeeze decay → parabolic-ratchet → breakeven → VWAP×2 → MC gating) that feed the four-flag priority resolver. The output of the loop is *not* an order: it's an append to `execution_queue` (`alpha_bot_execution.py:1459-1469`) which is drained once at the end of the symphony pass.

The "no portfolio-level autonomous math" stance is enforced by code archaeology rather than by inline guards. `DECISIONS.md` §DE-S3-004 binds: *"All autonomous port-level decision math is removed from production code. Deleted: `engine/multi_cycle.py`, `engine/port_selector.py`, `engine/port_aggregator.py`, `engine/dual_altitude.py`."* The user's rationale — recorded in `MEMORY.md` `[[project-port-level-deprecation-directive]]` (2026-05-26) — is that the management surface collapses to symphony-level only after Sprint 2 Wave 2a; port-level metric config, sellouts, port-mode autotuner and port-state dashboard math were deprecated in Sprint 3 because they had no replay-validation track and were "explicitly flagged as untrustworthy" (`docs/audit/sprint-3-port-removal-manifest.md §0 row 3`).

The exit decision for a single symphony resolves through `math_engine.resolve_trigger_priority` (`math_engine.py:736-759`). The four exit flags (`is_vwap_broken`, `is_tp_hit`, `is_vwap_bleed_broken`, `is_trailing_stop_hit`) are evaluated independently by their respective pure math functions earlier in the loop; the resolver fires only when at least one is True (`alpha_bot_execution.py:1428-1441`) and uses a fixed string-keyed canonical priority list `_TRIGGER_PRIORITY_ORDER = ["VWAP Breakdown", "Take-Profit", "VWAP Bleed Cut", "Trailing Stop"]` (`math_engine.py:728-733`). The `(winner, also_true)` tuple is the engine's commitment to honest co-firing telemetry: the winner triggers the exit, but the `also_true` companions are persisted alongside so a reviewer can detect when two layers were simultaneously satisfied — a signal the resolver was load-bearing on that cycle. When **no** flag fires, the loop ends with a `record_cvar_diagnostic` telemetry write (`alpha_bot_execution.py:1417-1426`) and "no-action" reduces to a state-update pass — high-water mark moves, breakeven counter advances, the symphony lives to see the next :00 tick.

## §2. Decision-vector inventory

Note on "six layers vs four triggers": project CLAUDE.md and `feature-plans/decision-science/README.md` §1 (hazard row G-3) refer to *"6 incumbent layers (vol-scaling, time-squeeze, parabolic ratchet, breakeven, VWAP×2, MC)"* — those are the upstream **math layers** that feed the **four-flag** priority resolver. The two are different abstractions: math layers compute features and intermediate states; the resolver selects among the four exit triggers any of those layers contributed to. Both tables are below.

### 2.b Four exit triggers (priority resolver)

| Priority | Trigger flag | Fired by which layer | Why this priority position | Justification source |
|---|---|---|---|---|
| 1 (highest) | **VWAP Breakdown** | VWAP×2 layer (`is_vwap_broken`) | Sharp portfolio VWAP cross after HWM = an active liquidity / regime-shift event; preempts everything | `math_engine.py:726` *"Canonical priority order: VWAP Breakdown > Take-Profit > VWAP Bleed Cut > Trailing Stop"*; `alpha_bot_execution.py:1434-1435` R3b comment |
| 2 | **Take-Profit** | MC gating (`tp_triggered_now` from `compute_tp_confirmation`) | Exceptional-gain signal: MC prob below `acc_TAKE_PROFIT_MC_PCT` AND return > 0 with 2-tick confirmation — wins over slower stops because the regime that fired it has already turned | `compute_tp_confirmation` shared by live + replay (`alpha_bot_execution.py:1264-1268`); D-C3a binding; council §G-3 |
| 3 | **VWAP Bleed Cut** | VWAP×2 layer (`is_vwap_bleed_broken`) | Slow-bleed below VWAP — slower than Breakdown, faster than the trailing stop in a low-vol drift | Threshold `VWAP_BLEED_MULTIPLIER` × `symphony_vol` (`compute_vwap_bleed_arm_threshold`); `VWAP_BLEED_TICKS` confirmation count (`alpha_bot_execution.py:1024-1026`) |

**Aggregation / tie-breaking.** `resolve_trigger_priority` builds `flag_map` keyed by trigger name, iterates `_TRIGGER_PRIORITY_ORDER` in order, returns `(fired[0], fired[1:])`. The winner is structural; co-fires populate `also_true` so the persisted record retains every flag that fired (`alpha_bot_execution.py:1467` — `also_true=also_true` field on the queued execution). This separates **decision** (one winner) from **telemetry** (every flag), which is the defensibility move: a Phase-2 reviewer can verify the resolver was load-bearing without losing co-fire evidence.

**Why this order.** No DECISIONS.md entry documents the *specific* ordering; the in-code comment at `math_engine.py:726-727` (*"Order matches H2 acceptance criteria (alpha_bot_execution.py:1081 comment) and the math audit"*) cites a historical H2 acceptance-criteria reference. The council synthesis treats it as the **incumbent** order — preserved verbatim under the G-3 hazard *"resolver kept and extended, never replaced, never collapsed."* See **§6 undocumented design choices** for the open question on whether the relative position of Take-Profit (above Bleed Cut) was ever argued from first principles.

## §3. Autotuner narrative

The autotuner runs end-of-day per symphony via `run_autotuner(bot_state, current_date_str, account_uuids, is_forced=False, spec_bundle_id)` (`autotuner.py:1283`). The **125-trading-day** window is the binding input: `synthetic_history.py:28-32` calls it the *"minimum replay-day floor: fewer than this and the validation fold is degenerate"*, and `autotuner.py:241-251` declares `TRAIN_RATIO=0.60 / VALIDATION_RATIO=0.20 / FROZEN_EVAL_RATIO=0.20`. The walk-forward methodology cites **López de Prado 2018 Ch. 7.4** as the held-out frozen-eval source-of-truth; the specific 60/20/20 ratio is acknowledged in code as *"an operator choice for AlphaBot's data scale (125 trading days); the held-out frozen-eval invariant derives from LdP 2018 Ch. 7.4 (**not the specific ratio**)"* (`autotuner.py:244-245`, `autotuner.py:1286-1289`). The cost is explicit: after `PURGE_DAYS=20` and `EMBARGO_DAYS=1` at both fold boundaries, the validation and frozen-eval windows shrink to *"approximately 4-5 usable days. This is an acknowledged tradeoff — the purge is methodologically correct and the short evaluation window is the cost of honest OOS reporting"* (`autotuner.py:1301-1307`). The 125-day window is therefore **not** chosen by theory; it is the live-data ceiling Composer/Alpaca provide, and the 60/20/20 is the operator compromise to extract any honest frozen-eval slice from it.

The **500-trial Optuna budget** appears at `autotuner.py:1569` (`study.optimize(objective, n_trials=500, n_jobs=_n_jobs)`). Its rationale is documented only indirectly: `autotuner.py:300-302` explains *"BHY rather than Bonferroni because Bonferroni at N~500 is brutally over-conservative"* — implying that 500 was chosen first and the haircut family chosen to match. The Phase-1 sweep at `autotuner.py:1950` runs `n_trials=100` (the "default Optuna trial floor" referenced in project CLAUDE.md Known Gotchas as the statistical-stability minimum). The gap 100→500 is therefore the difference between "stability floor" (sweep) and "production search" (per-symphony walk-forward), but **no DECISIONS.md entry argues 500 specifically over 250 or 1000** — see §6.

**CRRA-EU as objective over Sharpe.** The migration replaces a "Sortino ratio with five hand-tuned loss-aversion multipliers" (`docs/handoff/decision-science-council-synthesis.md` §2.1 line 119) with a single theory-grounded CRRA expected utility. The decisive argument is in council synthesis §2.1: the prior objective had **five undocumented hand-tuned constants** with no decision-theoretic justification, while CRRA reduces the entire risk-aversion shape to **one** parameter `gamma` that can be **frozen by theory (Merton 1969 / Samuelson 1969)**, registered in `spec_bundles`, and **never** tuned by Optuna. The per-trial t-stat is *re-derived* (S-2 binding) so the haircut is honest: `compute_crra_eu_tstat(U_series) = mean(U)/(sd(U)/√T)` (`autotuner.py:367` + `math_engine.py` CRRA constants `WEALTH_ARG_FLOOR=0.001`, `CRRA_LOG_UTILITY_GAMMA_TOL=1e-9`). The W-H4 wealth-argument floor lives on **input W**, not output U (council synthesis §3.9 — *"Floor is on INPUT W; never on output U (flooring U inflates the t-stat — anti-conservative)"*). Reusing `compute_sortino_tstat` for the CRRA objective is the **H-6 category error** explicitly forbidden (`autotuner.py:379-385` docstring).

**NN1 spec-freeze.** The "spec-freeze" wall prevents Optuna's TPE from touching theory-frozen facets. `autotuner.py:52-95` enumerates the freeze-discipline enum (`THEORY`, `MANDATE`, `STYLIZED_FACT`, `CALIBRATION`, `BACKTEST_SELECTION`); `NN1_HONEST_DISCIPLINES = frozenset({…})` excludes `BACKTEST_SELECTION` and `OOS` because *"P&L-frozen = uncounted test event = BHY haircut a lie by omission"* (council synthesis §2.5; `feature-plans/decision-science/README.md` Cross-cutting hazard row 1). The wall is structural: `validate_search_space_nn1()` (`autotuner.py:1183-1186`) and `validate_nn1_compliance(spec_bundle_id)` (`autotuner.py:1353-1360`) both run **before** `optuna.create_study` so a leaked facet raises rather than being silently toured. What NN1 prevents: the `gamma`, `utility_family`, `wealth_argument`, M3 curves, M2 alpha/window, block length, regime features, hysteresis thresholds, and lambda from being **chosen by best-of-N** rather than theory — a P&L-selected facet would contribute to the multiple-testing count S, inflating `N_effective` and the FDR-gate bar, but if the facet is omitted from the ledger the inflation never happens and the haircut undercounts. NN1 is therefore not a numerical correction but a **provenance invariant**: every facet on the wall is documented in `spec_facets` with `freeze_discipline ∈ NN1_HONEST_DISCIPLINES` or the autotuner refuses to start.

**BHY haircut + `N_effective`.** The autotuner runs 500 trials and deploys the best — the canonical multiple-testing trap. The chosen correction is Harvey & Liu 2015 Benjamini-Hochberg-Yekutieli (BHY) FDR-controlled haircut, cited at `autotuner.py:289-297`. The honest count is `N_effective = N_optuna + S`, where `S = Σ n_configs_searched` over researcher-degree-of-freedom ledger rows with `evidence_source = 'BACKTEST_SELECTION'` (`compute_n_effective` at `autotuner.py:489-525`; council synthesis §2.2). The **additive** structure (`N_optuna + S`, never `× S`) is the council's defensibility choice: the additive form is identical to today's haircut in the NN1-honest steady-state (S=0), so the migration is byte-identical until a researcher actually adds a P&L-frozen facet — making BHY-honesty an opt-in cost rather than a baseline tax. The problem this solves: **best-of-N inflation** — the best-of-500 Sortino is upward-biased by selection, and silently deploying it produces a strategy whose live performance is systematically below its backtest performance. BHY caps the false-discovery rate at `HARVEY_LIU_FDR_Q = 0.05` (`autotuner.py:299-304`). The Bonferroni alternative was rejected as *"brutally over-conservative at N~500"* (`autotuner.py:302`).

## §4. Advisor producers narrative

The Sprint 3 producers are **three observers, not one verdict.** `advisors/overfitting_conscience.py` (Overfitting Conscience, OC), `advisors/spec_critic.py` (Spec Critic, SC), and `advisors/divergence_explainer.py` (Divergence Explainer, DE) each emit independent `AdvisorObservation` rows via `database.insert_advisor_observation`; they share **no synthesized verdict**. The architectural reason for keeping them independent is the **wall integrity rule** documented in all three modules: *"All DB reads flow through `database.advisor_ro_query` (architecture constraint; enforced by CI lint test `test_advisors_module_uses_advisor_ro_query`). Direct connection access is prohibited"* (`advisors/overfitting_conscience.py:13-18`, `advisors/spec_critic.py:21-24`, `advisors/divergence_explainer.py:23-28`). A combined synthesis would have to either (a) cross the wall to query observations the synthesiser did not itself produce — breaking the read-only producer model — or (b) couple the three producers' termination, breaking their independent error containment.

**Overfitting Conscience** consumes the `researcher_dof_ledger` BACKTEST_SELECTION accumulator (S counter) against the run's `N_effective` budget. Three indicators (`advisors/overfitting_conscience.py:7-13`): I-1 *any* S>0 row → WATCH or BREACH; I-2 `S/N_optuna > 0.10` → BREACH; I-3 monotonic S growth across consecutive runs on the same symphony → WATCH. The threshold `S_RATIO_BREACH_THRESHOLD = 0.10` is sourced from *"council synthesis §2.5 NN1 spec-freeze hazard; Sprint 3 dispatch brief §I-2"* (`overfitting_conscience.py:40-41`). OC is the live consumer of the BHY haircut's accounting: an honest run keeps the ratio at zero; a leak is visible immediately.

**Spec Critic** examines the `spec_bundles` and `spec_facets` rows for structural integrity. Four indicators (`advisors/spec_critic.py:5-14`): I-1 required Phase-1 THEORY facets present (`gamma`, `utility_family`, `wealth_argument`); I-2 every facet has a recognised `freeze_discipline`; I-3 facet `frozen_at` < `SPEC_AGE_WATCH_THRESHOLD_DAYS` old (advisory); I-4 no Phase-2 facets seeded prematurely (`PHASE2_FACET_NAMES`). I-2 is **default-deny** — any unrecognised discipline → BREACH — which is the forward-compat defence-in-depth that catches a facet introduced by a future migration whose discipline string was typo'd or invented. The verdict resolution is explicit (`advisors/spec_critic.py:17-21`): BREACH > WATCH > CLEAR.

**Divergence Explainer** is the most constrained producer. It surfaces **two honest CVaR values** under the §B "operator-optional second window residue" — and **MUST NOT** surface any signed divergence quantity. The forbidden-keys list in the module docstring (`advisors/divergence_explainer.py:14-19`) enumerates: *"divergence", "signed_divergence", "cvar_diff", "cvar_delta", "window_divergence", "divergence_pct", "delta"*, plus any semantic equivalent (spread, gap, difference, diff). This carries `DECISIONS.md §DE-S3-005` (the CVaR-divergence REJECT) and `MEMORY.md [[project_cvar_divergence_validation_wall]]` into every produced row. The rejected idea: a signed CVaR-divergence detector that would compare the standard kNN window against a second (regime-shifted) window and surface a number an operator could treat as a tradable signal. The reason it was rejected — from the validation-wall memory — is that *"validate a detector not an estimate"* relocates the data wall onto the **~5-15 independent regime-shift count** (correlated with the same tail days the CVaR estimator already exhausts), so the divergence detector does **not escape** the data wall, it just hides it behind a different question. DE survives **only** as a two-honest-numbers operator diagnostic.

**Why Narrator is deferred.** `MEMORY.md [[project_sprint_3_scope_and_team]]` (2026-05-27) records that Sprint 3 covers OC + SC + DE; Narrator is deferred. The architectural reason is in council synthesis §3 (binding context item 3 of the README): *"Regime & Decision Narrator advisor role is Phase-2-conditional. Structurally inapplicable at Phase 1 (no drift to narrate)."* Phase 1 ships the CRRA-EU offline objective + the CVaR diagnostic — neither of which **changes which exit the engine fires** — so there is no drift between the legacy and the new decision-vector for a narrator to explain. Narrator activates when Phase 2 unlocks the live CVaR co-signal and the two decision paths can diverge per cycle. `DECISIONS.md §DE-S3-003` binds this deferral as enum-retained: *"The `NARRATOR` advisor role enum value is retained in the codebase with an inline deferral comment. No code is deleted"* — visible at `app.py:2419` (*"NARRATOR — DEFERRED per Sprint 3 scope — producer not yet shipped"*).

## §5. Read-only-dashboard rationale

The dashboard's "no live trades" stance has three layers of enforcement, each cited.

**Architecture constraint.** Project CLAUDE.md Architecture Constraint 2: *"Dashboard is a read-only operator surface — never an action surface for live trades."* This is the **invariant** every other layer enforces.

**Mechanical enforcement.** SQLite read-only mode at the driver level: `database.py:77` *"Opens via SQLite URI with `?mode=ro` — read-only enforced at driver level."* All dashboard-side accessors call `get_ro_connection()` (e.g. `database.py:889` *"Uses get_ro_connection() per architecture constraint 5 (dashboard read-only)"*) so a Flask request thread literally cannot execute a `BEGIN…COMMIT` write transaction against the state DB. The single exception is settings mutation through `/api/settings` (`app.py:2036`), which writes only operator-config rows — never positions or trades.

**Code-archaeological enforcement.** The `/api/trigger` POST handler (`app.py:1550-1554`) is the canonical "side-effect ban" guard: *"Dashboard side-effect ban: routes must not spawn the engine (arch constraint 2). The scheduler is the only legal engine spawner."* The handler returns success with the message *"Manual trigger disabled — use the scheduler."* — visible at runtime so any operator who clicks the legacy "manual trigger" button receives explicit feedback that the path is closed. `/api/force_eod` and `/api/sell_account` exist (`app.py:1574`, `app.py:1820`) but the latter is the documented `KEEP-MANUAL` button per the port-removal manifest §0 — *"MANUAL `perform_account_liquidation` button"* — and an operator must click it; the engine never autonomously fires it.

**Why `port_state` is displayed (KEEP-DISPLAY) but port-decision math removed.** The Sprint 3 port-removal manifest §0 documents 9 KEEP-DISPLAY sites alongside 6 REMOVE sites (`docs/audit/sprint-3-port-removal-manifest.md` lines 18-23). The rationale is at lines 170-187 — the dashboard reads `port_state` for all accounts and includes it in `/api/state` for the observability panel, *"No decision is made from this read; the result is serialised into the JSON response and consumed only by templates for display."* `DECISIONS.md §DE-S3-004` codifies the binding split: *"All autonomous port-level decision math is removed from production code … `engine/exit_authority.py` is retained as display-only badge helpers (AX-2 badge + restart_notice). Port state schema rows … are preserved per additive-first policy."* So the schema rows stay (additive-first migration policy: never destructive in one step — project CLAUDE.md Coding Standards bullet 4) and the read-only display path stays (operator observability is non-negotiable), but every **dispatch** path — `aggregate_to_port`, `build_port_signal`, `select_symphony_with_mc_gate`, `execute_sell_to_cash` on the autonomous branch — is deleted. The display badge in `engine/exit_authority.py` (`docs/generated/engine_exit_authority.md` §Overview) reads `EXIT_AUTHORITY` from the environment but the value is **display-only**: *"no per-minute dispatch decision is derived from it."* This is the disciplined version of "remove the surface, keep the photograph."
