## Overview

`static/index.js` is the browser-side controller for the operator dashboard (`/`). It runs as an IIFE. Key responsibilities:

- **State polling** — `loadState()` fetches `/api/state` and calls `updateDashboard(data)` on success. Fires once on `DOMContentLoaded` and then on a 30 s `setInterval` as the resilience fallback.
- **Event-driven updates (primary path)** — subscribes to `/api/events` via the `EventSource` API. On a `cycle-complete` event, calls `loadState()` immediately so the dashboard reflects the engine's just-completed cycle without waiting for the next 30 s poll tick.
- **Staleness cue** — `showConnectionLost()` flips the engine badge and `data-as-of` element to a visible error state when `loadState()` fails, so the operator knows displayed numbers are frozen rather than silently stale.
- **Account-basis honesty markers** — `renderAccountBasisChip()`/`renderAccountBasisFreshness()`, called from `updateComparisonRows()` every poll, surface the backend's stale-account/value-weighted-floor state on the Today/Cumulative comparison rows plus a dedicated freshness stamp (`DE-AUDIT-BL4-001`).
- **Guard-alpha dollar-saved panel** — `fetchGuardAlphaSummary(windowToken)` calls `/api/guard-alpha-summary` (optionally windowed, `DE-GAS-COHERENCE-001`) once on page load and on every window-picker click, populating the `#dollar-saved-headline` / `#dollar-saved-verb` / `#guard-event-count` / `#dollar-saved-basis-label` elements (plus the realized-basis and net-of-friction siblings).
- **Window picker** — `fetchWindowedStrip(token)` calls `/api/strip/<token>` when the operator clicks a time-window button; re-windows only the hero guard-alpha headline without a full page reload. As of `DE-CLOSED-BOUNCE-001` (revise round), it does NOT re-window ANY of the three comparison rows (Today/Cumulative/MDD) — all three are only ever sourced from a genuine `/api/state` poll (see Comparison rows below). As of `DE-GAS-COHERENCE-001`, the SAME click also calls `fetchGuardAlphaSummary(token)` so the $-saved panel re-windows in lockstep.
- **Guard-alpha headline fallback** — `renderGuardAlpha(data, _fromStrip)` reads the server-computed windowed VW `guard_alpha` from `portfolio_strip`; when absent (e.g. a closed_frozen default-window computation failure, or `weight_sum==0`) it falls back to `fetchWindowedStrip('30d')` to backfill just the headline — never any comparison row (`DE-CLOSED-BOUNCE-001`).
- **MC dial + detail render honesty** — `renderMcDial()` and the detail-view Risk Math panel actively render an explicit exited/"—" state for a triggered symphony instead of scanning history for (or freezing on) a stale pre-trigger reading (Math Remediation F7, `DE-MATH-F7-001`).
- **Section-count badges** — `updateSectionMeta()` reads `data.state`/`data.bot_state` (present on every `/api/state` branch) rather than the sometimes-absent `data.symphonies`, so the active/standby counts don't collapse to 0 on the closed/frozen branch (F-011).
- **Comparison rows** — `updateComparisonRows()` re-renders the Today/Cumulative/MDD rows ALL-OR-NOTHING: all three render together ONLY when the payload carries `data_as_of` — i.e. only from a genuine `/api/state` poll, never from a `fetchWindowedStrip` wrapped payload (`DE-CLOSED-BOUNCE-001`, revise round — the original cycle gated only the Cumulative row; review found Today/MDD shared the identical bounce risk). The Cumulative row sources the lifetime `cumulative_return` only, preserves a genuine `null` through to the honest empty-state instead of coercing it to a false zero (F-016 locus 1), and (as of `DE-AUDIT-BL4-001`) the function additionally renders the account-basis honesty chip/freshness markers described above, under the same `data_as_of` gate.
- **Hero chart axis + label** — `renderHeroChart()`'s Chart.js config keeps the y-axis visible so the chart's day-by-day cumulative series can't be visually mistaken for the adjacent lifetime scalar headline (F-025).

## API Reference

### `loadState()`
Fetches `GET /api/state` and calls `updateDashboard(data)` on success. On any fetch or JSON-parse error, calls `showConnectionLost()` and logs to console.

Called on:
- `DOMContentLoaded` (initial load)
- Every `POLL_INTERVAL_MS` (30 000 ms) via `setInterval` (resilience fallback)
- Every `cycle-complete` SSE event (primary path)

### `showConnectionLost()`
Visible staleness cue (AC-8). Targets three real DOM element IDs (from `_chrome.html:51-53` and `index.html:846`):
- `#engine-status-dot` — background color set to `'var(--studio-neg, #e33)'` (red dot).
- `#engine-status-label` — text set to `'Connection Lost'`.
- `#hero-data-as-of` — text set to `'connection lost'`.

Called by `loadState()` on fetch failure. Does NOT suppress or replace the poll retry — `setInterval` continues, so the badge self-heals on the next successful poll.

**Prior defect (fixed this cycle):** The original implementation targeted `#engine-status-badge` and `[data-testid="data-as-of"]`/`.data-as-of` — selectors that do not exist in the production template. `getElementById` returned `null` for all three; the staleness cue was silently a no-op: the operator saw no visual indication of a dropped connection.

### `updateSectionMeta(data)`
Computes the active/standby section-count badges from the live symphony set.

**F-011 fix (`DE-DISPLAY-TRUTH-001`, 2026-07-21):** previously read `Array.isArray(data.symphonies) ? data.symphonies : []` — `data.symphonies` genuinely does not exist on the closed/frozen `/api/state` branch (`app.py` emits `state`/`bot_state` only there), so the badges deterministically read 0 (empty array) whenever the market was closed. Fixed to read `data.bot_state || data.state` — present on BOTH branches — filtered to symphony-shaped entries (`typeof v === 'object' && 'name' in v`), matching the same filter `app.py` itself applies (`isinstance(v, dict) and "name" in v`) since `state`/`bot_state` also carries flat non-symphony metadata keys (e.g. `last_successful_cycle_at`) at the top level that a naive `Object.values()` would miscount as a phantom standby symphony.

### `renderAccountBasisChip(testid, ps)` / `renderAccountBasisFreshness(ps)` (`DE-AUDIT-BL4-001`, 2026-08-05)
New render helpers (placed between `setPosNeg` and `updateComparisonRows`), surfacing three account-basis honesty markers the backend already computed and serialized into `portfolio_strip` — `ps.basis`, `ps.account_basis_stale`, `ps.account_basis_as_of` (`app.py:1749-1758` live / `:2382-2387` frozen, `DE-EOD-BASIS-001`) — that had **zero consumers anywhere in this file** before this cycle (confirmed by direct grep against the pre-fix `updateComparisonRows` body). Both are called from `updateComparisonRows(data)` on every poll cycle.

**`renderAccountBasisChip(testid, ps)`** — looks up `document.querySelector('[data-testid="' + testid + '"]')`; a missing element is a silent no-op. Called twice per poll: once with `'comp-today-basis-chip'`, once with `'comp-cumulative-basis-chip'`. **Never called for the Max DD row** — Max DD is not account-basis-derived (`ps.max_drawdown` has no `basis`/`account_basis_stale` dependency), so no chip element exists there at all.

Two-label honesty contract, priority-ordered, never conflated on one chip:
1. `ps.account_basis_stale` truthy → `"Stale account data (as of " + ps.account_basis_as_of + ")"`, `hidden = false`.
2. Else `ps.basis === "value_weighted"` → `"Value-weighted floor — degraded account fetch"`, `hidden = false`. No timestamp — the value-weighted-floor tier (narrow daemon-restart-only window per D2) has none to disclose, and none is fabricated.
3. Else (the common healthy-fetch case) — `textContent = ''`, `hidden = true`.

**Priority rule when both flags are true simultaneously (approved team-lead ruling): STALE wins.** This is the more actionable disclosure to the operator and the only way to guarantee the chip's text never conflates the two conditions on a single element.

**`renderAccountBasisFreshness(ps)`** — targets `document.getElementById('account-basis-as-of')`, a dedicated element (`templates/index.html`, outside the hero chart-legend region) structurally distinct from `#hero-data-as-of` (whose engine-cycle-anchored contract, established by `showConnectionLost()`, is completely untouched by this feature). Populates `'account data as of ' + ps.account_basis_as_of` and un-hides ONLY when BOTH `ps.account_basis_stale` AND `ps.account_basis_as_of` are truthy; otherwise the element is cleared and hidden — the value-weighted-floor tier has no honest timestamp to disclose for this element either.

**Every-poll reset, non-vacuity-tested:** since `updateComparisonRows` runs against the SAME persistent live DOM on every poll (not a fresh render), both helpers' "else" branches are load-bearing — they are what un-shows a chip/freshness stamp left over from a prior poll when the account basis genuinely recovers. `TestStaleToHealthyTransitionResetsChipsAndFreshness` (sufficiency-review pin, commit `b82de309`) drives `updateComparisonRows` through two sequential payloads against one DOM stub (stale→healthy, stale→value-weighted-floor) and asserts the reset actually fires — a weaker implementation that renders correctly per-scenario-in-isolation but omits the reset branch would pass every other test in the suite while leaving a stuck stale chip after a real recovery.

### `renderGuardAlpha(data, _fromStrip)`
Renders the `#guard-alpha-headline` element from `portfolio_strip.guard_alpha` — the server-computed windowed VW guard alpha (`ps.guard_alpha`, set by `_compute_portfolio_strip`/the closed_frozen branch's own default-window block, both `app.py`; see `docs/generated/app.md`). Deliberately does NOT derive `guard_alpha` from `cumulative_return.dry_run - cumulative_return.if_held` — those fields can be on different bases (windowed VW bot vs. account-basis held), which would fabricate a wildly wrong figure instead of the correct one.

**Fallback (`DE-CLOSED-BOUNCE-001`, 2026-08-25):** when `ps.guard_alpha` isn't a number, calls `fetchWindowedStrip('30d')` to backfill the headline from `/api/strip/30d` (guarded by `_fromStrip` against re-entry — `compute_windowed_portfolio_strip` can itself return `guard_alpha: null` when `weight_sum==0`, and without the guard that would loop forever). Pre-fix, `guard_alpha` was ABSENT on every closed-market poll (the closed_frozen branch's inline `portfolio_strip` never set it), so this fallback fired on every single closed-market tick — and `fetchWindowedStrip`'s wrapped windowed-VW payload, passed through to `updateComparisonRows` as an unintended side effect, raced a genuine `/api/state` poll for the comparison rows on every tick, bouncing them between the correct account-basis values and incorrect windowed ones. **Two independent fixes close this, and BOTH matter** (the fallback still fires legitimately post-fix — a new symphony, or a window with too little `shadow_history`, both leave `guard_alpha` genuinely `null` even with the server leg working correctly): the closed_frozen branch now populates `guard_alpha`/`window` itself in the normal case (`app.py`, see `docs/generated/app.md`), so this fallback is a rare edge-case path again, not an every-poll default; and separately, `updateComparisonRows` (below) now structurally excludes ALL THREE comparison rows — not just Cumulative — from ANY payload this fallback's `fetchWindowedStrip` call produces, so even when the fallback does fire (the genuine edge case), it can no longer touch any of them. The pre-fix comment here claimed the fallback populated the cumulative row "with correct windowed VW values" — that was the wrong mental model that produced the bug; a windowed value is never correct under a row SSR-labeled "lifetime". See `DE-CLOSED-BOUNCE-001` in `DECISIONS.md`.

### `updateComparisonRows(data)`
Renders the Today / Cumulative · lifetime / Max DD comparison rows (bot vs. held bars, per-row alpha), ALL THREE together, ONLY when the payload carries `data_as_of` (`DE-CLOSED-BOUNCE-001`, see below). On a payload lacking `data_as_of`, none of the three rows' DOM is touched at all.

**Account-basis honesty markers (`DE-AUDIT-BL4-001`, 2026-08-05; gated `DE-AUDIT-BL4-001` addendum, 2026-08-05):** at the top of the function, immediately after destructuring `var ps = (data && data.portfolio_strip) || {}`, three calls run before the rest of the row-rendering logic -- but ONLY when `'data_as_of' in ps`:
```js
if ('data_as_of' in ps) {
    renderAccountBasisChip('comp-today-basis-chip', ps);
    renderAccountBasisChip('comp-cumulative-basis-chip', ps);
    renderAccountBasisFreshness(ps);
}
```
**Why the gate exists (live-render-gate-found bug):** this function has TWO production callers -- `loadState()`'s `/api/state` poll AND `fetchWindowedStrip(token)`'s windowed-strip re-render, which fires after EVERY state poll (see below). The windowed-strip payload (`analytics.compute_windowed_portfolio_strip`) is EXACTLY 8 keys -- `today_change`/`cumulative_return`/`max_drawdown`/`vol_bot`/`vol_held`/`guard_alpha`/`insufficient_history`/`window` -- and NEVER carries `basis`/`account_basis_stale`/`account_basis_as_of`. Before this gate, the three helper calls ran unconditionally on every `updateComparisonRows` invocation, so every windowed-strip tick (which always lacks the 2 flags) silently wiped a genuinely-stale chip the preceding state poll had just set -- caught by the PM's live render gate, not by the Node-harness suite, which never exercised the second caller. `'data_as_of' in ps` is a real structural discriminator: `_compute_portfolio_strip` sets it unconditionally on every `/api/state` poll (live success, exception-fallback, frozen success, frozen except-fallback, waiting-response injection, and open-market paths all carry it -- `bl4review`'s exhaustive producer-path trace), and the windowed-strip producer never sets it. A first discriminator proposal -- gating on literal presence of the account-basis keys themselves -- was falsified: a genuinely healthy, full-shape state poll has the IDENTICAL "no basis, no account_basis_stale" shape as a windowed-strip poll in the common case, so presence alone cannot distinguish the two payload shapes. See the dedicated section above for the two helpers' full contract; zero change to the existing Today/Cumulative/MDD value-rendering logic below this point.

**"Bot" simulation qualifier (AC-4, `DE-AUDIT-BL4-001`):** the `title=` attribute disclosing "Simulated (shadow-history) trajectory — not realized account P&L" on both `comp-{today,cumulative}-bot-text` spans is set server-side in `templates/index.html` (static markup, not JS-injected) — this function does not touch it; documented here because the qualifier's underlying VALUE (`row.values.dry_run`) is exactly what this function renders into those same spans. Value format is unchanged — only the tooltip attribute was added.

**F-014 fix (`DE-DISPLAY-TRUTH-001`, 2026-07-21):** the Cumulative row's `values:` previously preferred `ps.windowed_cumulative_return || ps.cumulative_return`. The row's own SSR label reads "Cumulative · lifetime" (`templates/index.html:961`) and is correctly sourced server-side — but this JS re-poll clobbered it with a windowed value every 30 s. Fixed to source `ps.cumulative_return` only, dropping the windowed preference entirely.

**Superseded by a stronger, all-rows gate (`DE-CLOSED-BOUNCE-001`, revise round, PR #136 `/code-review` finding #1, 2026-08-25):** F-014's fix closed the case where `updateComparisonRows` itself explicitly preferred a windowed field — but it didn't (and couldn't) stop a DIFFERENT function's fallback (`renderGuardAlpha`, above) from reaching this function with a windowed-strip wrapped payload whose OWN fields are windowed VW-basis under the same field names as a real poll's. This cycle's ORIGINAL fix (HEAD `8b0ad603`) gated only the `cumulative` entry (`rows.splice(1, 0, {...})` inside `if ('data_as_of' in ps)`) — but review finding #1 traced that `today`/`mdd` share the identical exposure: when `guard_alpha` is genuinely `null` even post-server-fix (sparse `shadow_history` / new symphony / an except-fallback), `renderGuardAlpha`'s fallback still fires and its wrapped payload's `today_change`/`max_drawdown` fields are on the SAME kind of mismatched basis/scope as `cumulative_return` was — Today can genuinely be account-basis on a real closed-market poll (when the account cache is warm, via `analytics.get_portfolio_today_change_account_basis`) vs. always-VW on `compute_windowed_portfolio_strip`; MDD stays VW-basis on both producers but can differ in trading-day/snapshot-vs-picker-window scope (no `get_portfolio_max_drawdown_account_basis` exists in `analytics.py` — MDD's divergence risk is a data/scope mismatch, not a basis-blend one, but the SAME `data_as_of` gate protects it regardless of mechanism).

`rows` is now built ALL-OR-NOTHING: `var rows = [];` by default, replaced with the full `[today, cumulative, mdd]` array ONLY inside `if ('data_as_of' in ps)` — the SAME discriminator `DE-AUDIT-BL4-001` established for the account-basis chip/freshness helpers above, now gating row INCLUSION uniformly rather than gating one row's splice. A `fetchWindowedStrip` wrapped payload never carries `data_as_of` (it's the 8-key `compute_windowed_portfolio_strip` shape, same as the account-basis gate's own discriminator proof), so `rows.forEach` runs over an EMPTY array on that payload — no row's DOM is touched at all, the last-correct values stay displayed instead of being overwritten or flickered to an empty state and back. Applies uniformly to EVERY `updateComparisonRows` caller, including the window-picker click handler (`fetchWindowedStrip`'s other real caller, see below) — a windowed value is wrong under any of these three labels regardless of who triggered the fetch. (Numerically invisible while the dataset is < 30 days old — the fix is pinned on the SOURCE EXPRESSION / row-inclusion logic, not a numeric-equality test.)

**F-016 locus 1 fix (`DE-DISPLAY-TRUTH-001`, 2026-07-21):** the bot/held extraction previously did `sentinelToNull(...) || 0`, discarding a genuine `null` before `fmtPct`'s own honest `'--'` branch could ever run. Fixed by dropping the `|| 0` coercion. Because `setPosNeg`'s `value >= 0` check evaluates `true` for `null` in JS (null coerces to `0` in a numeric comparison), every downstream `setPosNeg` call and the delta-alpha (`α`) calculation are now explicitly null-guarded too — a `null` bot/held value skips color-classification and renders `α --` rather than being silently treated as positive/green. See `DE-DISPLAY-TRUTH-001` in `DECISIONS.md` for the companion 3rd F-016 locus (`app.py`'s `_tc_cr_mdd_floats`, the opposite failure direction) this cycle also fixed.

### SSE subscription (DOMContentLoaded block)
```js
if (typeof EventSource !== 'undefined') {
    var _es = new EventSource('/api/events');
    _es.addEventListener('cycle-complete', function () { loadState(); fetchGuardAlphaSummary(_heroWindow); });
    _es.onerror = function () { /* silent — poll fallback handles reconnect */ };
}
```

Registered alongside the `setInterval` in the `DOMContentLoaded` callback. Behavior:
- **Primary update path:** `cycle-complete` fires within ~1 s of engine subprocess exit; `loadState()` fetches fresh `/api/state` before the next 30 s poll would fire. As of `DE-GAS-COHERENCE-001`, the same event also re-fetches the $-saved panel at the currently-active window token (was a bare `fetchGuardAlphaSummary()` call, always all-time).
- **Auth failure:** if `/api/events` returns 401, `EventSource.onerror` fires silently; the 30 s poll continues as the sole update path.
- **Connection drop / daemon restart:** `EventSource` retries automatically (browser built-in retry with exponential backoff). During the reconnect window the 30 s poll keeps state live.
- **Unsupported browser:** the `typeof EventSource !== 'undefined'` guard skips SSE entirely; the existing poll is the only update path. No visual breakage.

### `fetchGuardAlphaSummary(windowToken)`
Fetches `GET /api/guard-alpha-summary` (optionally `?window=<windowToken>`, `DE-GAS-COHERENCE-001`, AC-11) once on `DOMContentLoaded`, on every `cycle-complete` SSE event, and on every window-picker click. Populates:

| Element | Field |
|---------|-------|
| `#dollar-saved-headline` | `'$' + Math.abs(data.cumulative_saved_dollars).toFixed(2)` (ABS magnitude, no sign character) or `'No guard events yet'`, colored `--studio-pos`/`--studio-neg` by sign |
| `#dollar-saved-verb` | `'saved'` (sign `>= 0`) or `'lost'` (sign `< 0`) -- a dedicated element, independent of the static "across"/"exits" caption text around it |
| `#guard-event-count` | `data.guard_event_count` |
| `#dollar-saved-basis-label` | `data.basis_label` |

Non-200 responses are silently ignored (advisory-only display). Does NOT clobber `#guard-alpha-headline`, which is owned by the windowed strip path.

The existing hero window-picker click handler (`var windowTokenMap = {...}`, which already re-fetches `/api/hero-chart` + the windowed strip on click) now ALSO calls `fetchGuardAlphaSummary(token)` on the same click -- previously the $-saved panel always showed the all-time sum regardless of the selected window. `_heroWindow`'s initial value changed from the bare number `30` to the string `'30d'` (`:7`) to match the string shape the click handler always assigns and the actively-highlighted 30d button, so the very first `fetchGuardAlphaSummary(_heroWindow)` call (on `DOMContentLoaded`, before any click) is windowed the same way subsequent calls are.

**Empty-state gating (review-found gap, fixed at commit `40b130e3`):** the initial GREEN commit (`ed4eebee`) rendered both net-of-friction blocks unconditionally -- so a `guard_event_count===0` / `realized_coverage.with_data===0` empty state could show a spurious `"$0.00"` on the net line right beside the gross line's honest `"No guard events yet"` / `"no realized data yet"`. `bl3review` caught this; `bl3test` pinned it RED via a real Node execution harness (source extracted by brace-counting, run against a synthetic DOM + stubbed `fetch()`, asserted on actual `textContent` -- a source-text-only assertion can't distinguish "genuinely gated on `guard_event_count`/`with_data`" from "the guard string happens to appear nearby"). ### `renderMcDial(symId, chartData) → void`
Renders the SVG MC dial (arc + percentage text) for every `[data-testid="mc-dial"][data-sym-id="<symId>"]` element on the page (`:852`).

**Exited/triggered branch (`:859`, Math Remediation F7, `DE-MATH-F7-001` AC-2):** when `chartData.triggered` is truthy, actively renders the honest exited state — arc `stroke-dashoffset` set to full circumference (`MC_CIRCUMFERENCE`) in a faint color, text set to `'—'` — and returns immediately, before the non-triggered branch's history scan runs. This is deliberate, not a fallback: a null-scan cannot distinguish "no data yet" from "exited", and would otherwise resurrect the last real pre-trigger `mc_prob` as if it were current.

**Non-triggered branch (unchanged logic, now only reached when `!chartData.triggered`):** scans `chartData.data` for the last non-null `mc_prob` (0-100 scale), falling back to top-level fields, and colors the arc by band (`< 15` warn, `> 80` dim, else accent).

**Two call sites, both now pass `triggered` explicitly:**
- The per-symphony chart fetch handler (`:334`) threads `data.triggered = sym.triggered` onto the fetched chart payload before calling `renderMcDial(sym.id, data)`.
- The poll-path `updateDashboard` loop (`:1075`) calls `renderMcDial(id, { triggered: sym.triggered, mc_prob: sym.mc_prob, data: [] })` **unconditionally on every poll** — the pre-F7 code only called this when `sym.mc_prob != null`, which froze the dial at its last-drawn state for an exited symphony (whose `mc_prob` is now honestly `null`) instead of updating it to the exited state.

### Detail-view Risk Math panel (chart-fallback + neutral reset, `DE-MATH-F7-001` AC-2)
Inside the detail-view chart data handler:
- **`mcProb` resolution (`:674`):** short-circuits to `null` when `sym.triggered` is truthy, skipping the backward null-scan over `data` entirely — same rationale as `renderMcDial`'s exited branch (a null-scan on mixed pre/post-trigger history would resurrect a stale reading).
- **`#dp-rm-mc-bar` neutral reset (`:711`):** when the resolved `mcProb` is `null` (Not-triggered-with-no-data OR triggered), the bar width is explicitly set to `'0%'` and its color to `cs('--studio-ink-faint')` — added so the bar never keeps showing a stale width/color from a previous render for a symphony that no longer has a real reading.

## Update Paths

Two update paths coexist. Both call `loadState()` → `updateDashboard(data)`:

| Path | Trigger | Latency |
|------|---------|---------|
| SSE (primary) | `cycle-complete` event from `/api/events` | ~1 s after engine cycle exit |
| Poll (fallback) | `setInterval` every 30 s | up to 30 s lag |

The SSE path is always attempted first. The poll continues running as an unconditional safety net — it is NOT disabled when SSE is active. On auth failure, SSE silently degrades to poll-only with no visible disruption.
