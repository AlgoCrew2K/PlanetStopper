# advisors/incubation

> Strategy Incubation Gate: a forward paper-tracking ledger that intercepts Strategy Builder gate-survivors before they surface as recommendations, tracks each on real forward market data for a minimum window, and only promotes candidates that clear a genuinely out-of-sample bar. Advisory-only, zero live-execution surface.

**Source:** `advisors/incubation.py`
**Last updated:** 2026-07-25 (new module, `DE-INCUBATION-GATE-001`)

## Overview

`advisors/incubation.py` closes the third and final graduated gate identified in `docs/research/methodology-validation-2026-07.md` (recommendation 3). Before this feature, a Strategy Builder candidate that cleared the FDR/PBO/SPY backtest gate (`advisors/backtest_gate_engine.py`) surfaced immediately as an operator recommendation on the Strategy Builder tab. That backtest is entirely retrospective — the candidate tree was itself generated by an LLM (`advisors/build_plan_generator.py`), which raises a structural risk the gate cannot rule out: the model may be pattern-matching against market history it was trained on, rather than discovering genuine edge. This module adds a mandatory forward-tracking stage between "passed the backtest gate" and "recommended to the operator": every survivor enters this ledger as `INCUBATING`, is tracked on real forward daily returns (paper — zero capital, zero execution) for `INCUBATION_WINDOW_TRADING_DAYS` (63) trading days, and is only `PROMOTED` to recommendation status if its forward performance clears an honest bar against SPY.

**The memorization-free rationale (AC-8).** Forward data collected after a candidate's admission timestamp did not exist yet when the generating LLM's training data was assembled — it post-dates the model's training cutoff by construction. This makes the promotion decision in `evaluate_promotion` the first signal anywhere in the Strategy Builder pipeline that cannot be explained by the model having memorized or pattern-matched the evaluation data. A candidate can look arbitrarily good on its backtest and still fail here — see the citation embedded at the promotion-decision code site (`evaluate_promotion`, "AC-8 lookahead-bias rationale" comment) and `DE-INCUBATION-GATE-001` in `DECISIONS.md`.

Off-execution-path, CC-2 lazy-imported from `app.py`'s daemon thread (never a module-level import from `app.py` or `alpha_bot_execution.py`). D-1 (never-raises) throughout. Zero change to the 1-minute engine decision path — structurally enforced by `tests/advisors/test_incubation_blast_radius.py` (17 tests: zero incubation-symbol references anywhere in `alpha_bot_execution.py`/`math_engine.py`, a positive control that the scan itself works, and a full-repo stray-reference sweep).

**Module placement (layering rule).** `database.py` is a lower layer this module imports FROM; it must never import FROM `advisors.*`. Because `register_incubation_candidate`'s cap-and-refractory enforcement runs inside `database.py`, the two constants that logic depends on (`MAX_INCUBATING`, `INCUBATION_REFRACTORY_DAYS`) live in `database.py`, next to that accessor — not here. The three constants this module owns (`INCUBATION_WINDOW_TRADING_DAYS`, `INCUBATION_MDD_BREACH_MULT`, `INCUBATION_MAX_FETCH_FAILURES`) are tick/promotion-only and never read by `database.py`. Same house convention as `math_engine.py`'s no-magic-numbers rule, applied here even though this isn't the math-engine module.

## Constants

All operator knobs — **never** Optuna- or advisor-tunable (the pipeline must not optimize its own forward-validation gate, same rationale as `autotuner.py`'s `SIM_EXIT_FRICTION_PCT`).

| Constant | Value | Meaning |
|----------|-------|---------|
| `INCUBATION_WINDOW_TRADING_DAYS` | `63` | Minimum forward trading days observed before promotion is possible (~3 months — the report cites ≥6-month allocator practice; this is the named, trivially-raised retail-pragmatic floor `[PM-ASSUMED]`) |
| `INCUBATION_MDD_BREACH_MULT` | `1.5` | Forward max-drawdown (positive pct magnitude) must stay ≤ this × the candidate's stored backtest MDD (also positive pct magnitude) before an early fail fires `[PM-ASSUMED]` |
| `INCUBATION_MAX_FETCH_FAILURES` | `5` | Consecutive tick fetch failures for one candidate before `EXPIRED` `[PM-ASSUMED]` |
| `_MIN_SPY_PAIRED_OBSERVATIONS` | `2` | Minimum SPY-paired (non-null `spy_return_pct`) observations required before a window-complete evaluation is trusted; below this, promotion `DEFERS` rather than judging benchmark-blind (mirrors `backtest_gate_engine`'s `_PBO_MIN_ALIGNED_DATES`-style guard) |
| `_SPY_TREE_NAME` | `"SPY Benchmark"` | Identical 100%-SPY tree name/shape as `strategy_builder_engine.py:993-998`'s own SPY-baseline construction — a shared convention, not a second one |
| `_MDD_BREACH_EPSILON` | `1e-9` | Float64-noise tolerance on the MDD-breach boundary comparison. Same value and rationale as `guard_preconditions.py`'s `_BOUNDARY_EPS`: quantstats' `max_drawdown` is pandas/numpy float64 arithmetic that can land a fraction of a ULP off an exact decimal boundary (empirically ~1.8e-15 off a -15.0%-exactly scenario); the epsilon only ever forgives sub-ULP noise on the non-breach side of the comparison — it can never mask a genuine breach, since any real-world MDD difference worth caring about is many orders of magnitude larger than `1e-9` percentage points |

`database.py` owns two more (see [database](database.md)): `MAX_INCUBATING = 20` (cap on concurrently-`INCUBATING` rows) and `INCUBATION_REFRACTORY_DAYS = 90` (a `FAILED`/`EXPIRED` hash cannot be re-admitted for this many days) — both `[PM-ASSUMED]`.

## `candidate_hash` convention — reuse, never fork

### `candidate_hash(tree: dict) -> str`

Tree-structural SHA-256 hash. Delegates directly to `community_strats._composition_hash(tree)` — this module does **not** carry its own hashing implementation, nor did it add a new public alias in `community_strats.py` (the implementer's choice, per the frozen contract, was to import the private name directly). A property test (`tests/advisors/test_incubation_admission.py::TestCandidateHashConvention`) pins two independent guarantees: (1) `advisors.incubation.candidate_hash(t) == advisors.community_strats._composition_hash(t)` for arbitrary trees (uuid-independence, structure-sensitivity), and (2) a **non-tautological** check that recomputes the expected hash inline using only stdlib `json`/`hashlib` (no import of `community_strats` at all) — proving the underlying algorithm (strip `id` keys → `json.dumps(sort_keys=True, separators=(",",":"))` → sha256 hex) is correct, not merely that two functions happen to agree with each other.

This is **not** `CandidateInfo.candidate_id` (`plan["plan_id"]`, an unrelated per-run UUID minted by the build-plan generator) and **not** `database.compute_composition_hash` (which hashes a `list[str]` of symphony IDs for portfolio-set identity — a different thing entirely).

## Admission — single wiring seam

### `admit_candidate(candidate_hash, tree_json, objective, provenance, backtest_mdd_pct) -> dict`

Engine-layer entry point for admitting one candidate. A thin pass-through to `database.register_incubation_candidate` (see [database](database.md) for the idempotency/refractory/cap contract it enforces) — this function exists purely so `strategy_builder_engine.py`'s Step-5 wiring has a fixed, stably-named advisors-layer call surface. Returns `{"admitted": bool, "status": str | None, "reason": str}`, the same shape `register_incubation_candidate` returns.

Cap-aware batch ordering (sort survivors by gate-time `oos_alpha` descending, then admit in that order so a `MAX_INCUBATING` cap naturally excludes the lowest-`oos_alpha` candidates first) is the **caller's** responsibility — `admit_candidate` only enforces the cap for whichever single call it receives.

**Wired at exactly one seam, not two.** Both the on-demand route (`POST /ai-advisor/strategy-builder/run`) and the weekly scheduler (`advisors/strategy_builder_scheduler.py`) already funnel through the same production call: `strategy_builder_engine.propose_strategies()`. Admission is wired inside that function's Step-5 survivor-persist loop (`advisors/strategy_builder_engine.py`, "Step 4b"; see [advisors/strategy_builder_engine](advisors_strategy_builder_engine.md)) — **not** duplicated at the route or the scheduler. A recon finding from `ga3-tw` caught that the original plan text described the admission adapter as "called from `strategy_builder_engine.propose_strategies` persistence path + the weekly scheduler," which read as two separate wiring points; since the scheduler itself calls `propose_strategies`, wiring admission at both would have double-admitted every scheduler-sourced survivor (once via the scheduler's own call site, once via `propose_strategies`'s internal one). The PM ruled the single-seam design before any RED test was written; `tests/advisors/test_incubation_admission.py` includes a source-guard test asserting `admit_candidate`/`register_incubation_candidate` are referenced from exactly one production call site.

For each screened survivor, `propose_strategies` computes `candidate_hash(info.tree)`, converts `info.metrics["max_drawdown"]` (quantstats' negative-fraction convention) to a positive pct magnitude via `abs(raw_mdd) * 100.0` (an unknown MDD degrades to `0.0` — a conservative choice: a 0% baseline makes the forward-MDD-breach comparison trip on the candidate's very first drawdown, rather than silently never firing), calls `admit_candidate`, and threads the resulting `candidate_hash` through to `_persist_survivor` as a new optional kwarg (see "raw_response contract" below). D-1: an admission failure for one candidate never breaks another's, and never breaks the pre-existing `_persist_survivor` persistence call (same try/except-and-log pattern as the shipped `insert_frontrunner_proposal` precedent a few lines below it).

**Idempotency + refractory rule** (enforced inside `database.register_incubation_candidate`, see [database](database.md) for the full state machine): a re-generated identical tree while `INCUBATING`/`PROMOTED` is a permanent no-op (clock never resets); a `FAILED`/`EXPIRED` hash within `INCUBATION_REFRACTORY_DAYS` (90) of its last status change is refused; past that window it re-admits via an UPDATE-in-place with a genuinely reset clock. `EXPIRED` is treated identically to `FAILED` for the refractory window — a `ga3-tw` coordination decision (not verbatim in the original plan text): both represent "this hash didn't make it," and the refractory rule's stated purpose (prevent re-generation from laundering a candidate past its own history) applies equally to either.

**Frontrunner Builder queuing is unaffected.** `_persist_survivor`'s existing, unconditional `database.insert_frontrunner_proposal` call (the AC-10 retrofit, `DE-FRONTRUNNER-001`) still fires for every non-rejected candidate regardless of incubation status — this feature only gates the Strategy Builder tab's recommendation badge, not the separate Frontrunner Builder operator-approval queue. The two surfaces are independent; this cycle changed neither the Frontrunner queue's trigger condition nor its own operator-approval-to-Composer-create path.

## Promotion evaluation — pure function

### `evaluate_promotion(forward_return_pct, spy_return_pct, backtest_mdd_pct, days_observed) -> dict`

```python
def evaluate_promotion(
    forward_return_pct: list[float],
    spy_return_pct: list[float | None],
    backtest_mdd_pct: float,
    days_observed: int,
) -> dict:
    ...
```

Pure — no DB, no network, no I/O of any kind (structurally enforced by an import guard in `tests/advisors/test_incubation_promotion.py`). `spy_return_pct` is date-index-paired with `forward_return_pct` (same length); a `None` entry marks a day the shared SPY call didn't cover that tick. Returns `{"decision": "PROMOTED" | "FAILED" | "DEFERRED" | "CONTINUE", "reason": str | None}` — `reason` is set only for `"FAILED"`.

**Decision order, evaluated every tick:**

1. **Early-fail (any day count, checked first, unconditionally):** compute `compute_quantstats_metrics(forward_return_pct)["max_drawdown"]` (reused from `analytics.py` — same call shape `strategy_builder_engine.py` already uses, no hand-rolled second drawdown loop). If non-`None`, convert to a positive pct magnitude (`abs(fraction) * 100.0`) and compare against `INCUBATION_MDD_BREACH_MULT * backtest_mdd_pct + _MDD_BREACH_EPSILON`. A breach returns `{"decision": "FAILED", "reason": "mdd_breach"}` immediately — a candidate does not need to wait for the window to complete to fail on a real drawdown blowup. A `None` MDD (quantstats' own "insufficient data" signal) is treated as "cannot evaluate this tick," **never** coerced to `0.0` (which would trivially prevent a breach from ever firing).
2. **Window not yet complete, no early-fail this tick:** `days_observed < INCUBATION_WINDOW_TRADING_DAYS` → `{"decision": "CONTINUE", "reason": None}`. The candidate stays `INCUBATING`; no status write.
3. **Benchmark-missing guard:** date-paired exclusion of `None` SPY days — a missing SPY day is excluded from **both** sides' compounding for that date, never silently treated as a `0%` day (mirrors `backtest_gate_engine`'s own SPY-alignment convention). If fewer than `_MIN_SPY_PAIRED_OBSERVATIONS` (2) SPY-paired observations remain after that exclusion, evaluation returns `{"decision": "DEFERRED", "reason": None}` — window-complete and MDD-clean is not enough; the candidate stays `INCUBATING` rather than being judged benchmark-blind.
4. **Window-complete evaluation (AC-8 lookahead-bias rationale — the promotion-decision code site):** compound each side's paired daily pct-scale returns via `_compound` (`prod(1 + r/100) - 1` — simple-return compounding, the shipped convention throughout this codebase, never log-return math; see `composer_backtest_client._extract_returns`'s own docstring). `alpha = candidate_cum - spy_cum`. This comparison is computed **only** over data observed strictly after the candidate's admission — which by construction post-dates the generating LLM's training cutoff, making it the first memorization-free signal anywhere in the pipeline. `alpha >= 0.0` → `{"decision": "PROMOTED", "reason": None}`; otherwise → `{"decision": "FAILED", "reason": "forward_alpha_negative"}`.

Golden-fixture math tests: `tests/fixtures/math/incubation_promotion_scenarios.json` (7 hand-derived scenarios — promote / alpha-fail / early-MDD-fail / benchmark-deferred / window-incomplete / alpha-zero-boundary / MDD-multiplier-boundary), consumed by `tests/advisors/test_incubation_promotion.py` (13 tests, no I/O or mocking needed since the function under test is pure).

## Daily tick — off-hours orchestration

### `run_incubation_tick() -> None`

Fetches forward data for every `INCUBATING` candidate, appends new trading-day rows, and applies promotion/early-fail transitions. Off-hours, off-execution-path, CC-2 lazy-imported from `app.py`'s daemon thread (registered at **03:30**, see [app](app.md)). D-1: a fetch/processing error for one candidate is isolated in a per-candidate `try`/`except` and never aborts the tick for the others (mirrors `perform_account_liquidation`'s per-symphony isolation precedent, `DE-PANIC-STOP-CONFIRM-001`).

**No windowed Composer API exists.** `composer_backtest_client.run_backtest()` takes no start/end date parameter — every call returns the candidate's **full-history** `daily_returns` series (`dict[ISO-date-str, float]`). The tick does not (and cannot) request "just today's segment." Instead, for each candidate, it re-fetches the full-history response every tick and extracts every ISO date key that is (a) strictly after that candidate's most-recently-recorded `trading_day` in `incubation_daily` and (b) a genuine `market_calendar.is_trading_day` (never a weekday proxy), appending one row per new date. This single loop is **also** the catch-up-after-gap mechanism at zero extra cost: a daemon down for N days simply yields N new date keys in the next tick's one `run_backtest` response, backfilled in that one call — no special-casing needed. **This design correction (recon finding "c") supersedes the original plan text's "windowed from admitted_at" phrasing**, which described an API shape Composer does not offer.

**Bill-bounded:** ≤ `MAX_INCUBATING + 1` Composer calls per tick — one shared SPY call plus one call per `INCUBATING` candidate (bounded because `get_incubating()`'s result set is itself capped at `MAX_INCUBATING`). An empty ledger makes **zero** Composer calls, not even the shared SPY call (there is nothing to compare it against) — see `TICK8` in `tests/advisors/test_incubation_tick.py`.

**Structural (not just loop-logic) idempotency.** The loop's "only dates after the last recorded day" filter *selects* which dates to attempt, but the actual duplicate-prevention guarantee is the DB layer: `incubation_daily`'s `UNIQUE(candidate_hash, trading_day)` constraint plus `append_incubation_day`'s `INSERT OR IGNORE` write. A `ga3-rev` review finding, promoted by the PM to a hard requirement, made this explicit: a tick re-run, an out-of-order response reprocess, or a full-history resend after a restart must produce zero duplicate rows even if the loop-selection logic is ever wrong — pinned by `tests/advisors/test_incubation_tick.py::TestNormalTick::test_rerunning_the_same_tick_response_twice_inserts_zero_duplicates` (calls `run_incubation_tick()` twice with the identical mock response, asserts `days_observed` is unchanged after the second call).

**Per-candidate flow (`_tick_one_candidate`):**
1. Parse `tree_json`; an unparseable tree logs a warning and skips this candidate this tick (never raises).
2. `run_backtest(tree)`. A raised exception is classified as a fetch failure (step 4 below).
3. `result.error` is inspected via `plan_tree_compiler._parse_envelope_status` — the **same** error-envelope parser `plan_tree_compiler.py` already uses to distinguish a genuine Composer 422 (tree no longer tradeable) from any other failure; this module does not invent a second parser. A 422 sets `status="EXPIRED"`, `status_reason="composer_422_tree_invalid"` immediately.
4. Any other fetch error (including a raised exception from step 2) calls `database.record_incubation_fetch_outcome(hash, ok=False)`, which durably increments `strategy_incubation.fetch_failure_count` and returns the resulting count. If that count reaches `INCUBATION_MAX_FETCH_FAILURES` (5), the candidate transitions to `EXPIRED`/`"fetch_failures_exhausted"`. **Storage lives in `database.py`; the threshold policy (what to do once the count is reached) lives here** — the same storage/policy split used throughout this handoff. A plain in-memory counter was explicitly rejected: it would silently reset on every `app.py` restart, defeating the "must survive across ticks/restarts" requirement.
5. On success: `record_incubation_fetch_outcome(hash, ok=True)` resets the failure count to 0 (even if the fetch yielded zero new date keys — e.g. a same-day re-run; a successful call is a successful call), new-day rows are appended per the algorithm above, and `evaluate_promotion` runs against the candidate's full recorded series (`database.get_incubation_daily_series(hash)`) with the resulting `PROMOTED`/`FAILED` decision applied via `set_incubation_status`. `CONTINUE`/`DEFERRED` apply no status change — the candidate simply stays `INCUBATING`.

The shared SPY series (`_fetch_spy_returns_pct`) is fetched once per tick using the identical 100%-SPY tree `strategy_builder_engine.py:993-998` constructs. On any SPY-fetch error, it degrades to `{}` — candidate fetches still proceed benchmark-blind for that tick (promotion evaluation itself then defers per the `_MIN_SPY_PAIRED_OBSERVATIONS` guard above); a SPY-only failure never aborts the tick.

## `raw_response` contract — the AC-5 live-join design

`advisor_observations` rows are append-only/immutable (no update/delete accessor exists). A status value frozen into `raw_response` at persist time would always read the admission-moment value forever — a candidate promoted or failed weeks later would still display "INCUBATING" on its original observation, an honest-looking badge that would in fact be lying. This is why `_persist_survivor` gains **exactly one** new additive key, `"candidate_hash"` (immutable, always correct — the same additive-blob precedent as the shipped `run_id`/`invocation_source`/`evidence_injected` keys already in that dict) — and deliberately **not** a frozen `"incubation_status"` key. Status is instead computed **live**, at render/API time, by joining that `candidate_hash` against the incubation ledger (`database.get_incubation_overview()`) — see `app.py`'s `_incubation_badge` and `ai_advisor_tab()` stamping, and the route's own `GET /api/incubation` (both in [app](app.md)). Existing consumers parsing old rows are unaffected — this is a new, ignorable key; a pre-feature survivor simply has no `candidate_hash` and renders no chip.
